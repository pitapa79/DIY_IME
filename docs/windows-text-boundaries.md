# Windows接続前の文字位置の検査例

Issue #28の実験用[example](../examples/utf16_positions.rs)。[IMEへの実装順序案](windows-ime-next-steps.md)の位置境界を、OS登録も追加依存もなく検査する。製品の公開位置API・キャレット移動・削除単位を採用する変更ではない。

## 実行と検査

```powershell
cargo run --locked --example utf16_positions
cargo test --locked --example utf16_positions
```

妥当なUTF-8の原文を借用し、そのコードポイント境界ごとにUTF-8バイト数・Unicode scalar value数・UTF-16コード単位数を記録する。検索はどの単位からでも同じ境界を返す。文字の途中、サロゲートペアの途中、範囲外を丸めて受け付けない。UTF-16の半開区間をUTF-8の半開区間へ変換する例も含む。

例の原文は `A𠮷か` + 結合濁点U+3099 + `🦀`。対応表は次のとおり。

| UTF-8バイト位置 | コードポイント位置 | UTF-16コード単位位置 |
| ---: | ---: | ---: |
| 0 | 0 | 0 |
| 1 | 1 | 1 |
| 5 | 2 | 3 |
| 8 | 3 | 4 |
| 11 | 4 | 5 |
| 15 | 5 | 7 |

UTF-16 `[1,3)` は `𠮷`、`[3,5)` は結合濁点を含む `が`。UTF-16位置2/6はサロゲートペアの途中として拒否する。空文字でも位置0、非空文字でも末尾の境界は有効である。逆順の範囲は並べ替えずにエラーとする。

検査は既知の表、UTF-8の各中間バイト、サロゲート内部、空/末尾/範囲外/逆順、制御文字、BMPの境目・補助平面の上下限を含む。さらに各有効UTF-8境界で、原文prefixの `chars().count()` / `encode_utf16().count()` と往復結果を照合する。異なる原文スナップショットの表が別であることも確認する。

## 適用範囲

- 表は借用中の**同じ原文**にだけ対応する。入力revision、変換結果、別アプリの文書に再利用する仕組みはない。ホスト実装では文書/入力の世代も照合する必要がある。
- `か` と結合濁点の間はコードポイント境界として有効だが、利用者の見た目の1文字やキャレットの移動先と同じとは限らない。書記素分割、選択/削除の方針、Unicode正規化は扱わない。
- 入力はRustの妥当な `&str`。不正なUTF-8バイトや孤立サロゲートを含む外部UTF-16を受け入れるAPIではない。TSFアダプターでの検査/拒否方法は別タスク。
- TSFの文書座標やrange自体を実装・検証していない。PacketのsourceSpanと出力の位置対応を推測しない。文書の絶対位置と、この原文内の相対位置も区別する。
- 構築は原文長に比例する時間とコードポイント数+1件のメモリ、検索は境界数の対数時間。このexampleには独自の入力容量上限・資源提供サービスを設けていない。外部入力へ接続する前にホスト側の上限を決める。

WindowsのUTF-16とコード単位の説明は、Microsoftの[Working with Strings](https://learn.microsoft.com/en-us/windows/desktop/learnwin32/working-with-strings)を参照（2026-10-27確認）。本例はその区別をRustの標準ライブラリで照合する。
