# 偽文書ホストの入力・確定・取消実験

状態: **未採用のホスト状態機械のexample**。[Issue #30](https://github.com/pitapa79/DIY_IME2/issues/30) と [Windows IMEへの実装順序案](windows-ime-next-steps.md)の小さな試作。OS登録、TSF/COM、キーイベント、実アプリへの入力は行わない。コア・Node・グラフ・依存・lockも変更していない。

[examples/ime_host_harness.rs](../examples/ime_host_harness.rs) は、標準Registryの `input.text` → `text.romaji-to-hiragana` を既存Engineで同期実行する。例のグラフは `input` / `romaji` という固定IDと `out` / `pending` を使う。任意のグラフへ適用できる製品のホストAPIではない。

## 実行

```powershell
cargo run --locked --example ime_host_harness
cargo test --locked --example ime_host_harness
```

例では `k → ky → kya → ky → 空文字 → n` の全文を順に渡す。preeditは `k → ky → きゃ → ky → 空文字 → n` となり、確定済み本文 `本文:` は変わらない。Commitのfinalize結果ができても、結果受取と文書適用が成功するまで本文へ追記しない。偽文書の失敗を1回注入し、入力を保持して再試行すると `本文:ん` を一度だけ確定する。その後、取消を挟んで明示的な計画切替・復帰を行う。

## 明示的な命令と状態

| 命令・段階 | この実験の動作 |
| --- | --- |
| ReplaceInput(String) | 全文スナップショットをcomposeで実行。新しい入力revisionを割り当てる。短い全文への置換で削除相当を試し、削除単位やキー割当を決めない |
| Commit | 現在の全文をfinalizeで実行し、確定意図付きの結果を作る。命令を処理しただけでは本文へ書き込まない |
| Cancel | 未送達・受取済みの古い要求を無効化し、自分が所有する偽preeditだけを消す。成功後にホスト入力を破棄し、確定済み本文は変えない |
| receive | 入力全文とmode/revision、計画版、run ID、文書コンテキスト/改訂、未確定セッション世代を照合して受け取る。古い応答は現在の受取済み結果を上書きしない |
| apply_ready | 同じ識別情報を再照合し、偽文書側でも対象stampとpreedit所有者を確認してから原子的に適用 |
| prepare | 既存Engineへ新しい計画を準備。未確定中でも稼働計画版は変わらない |
| activate / rollback | 未確定セッションがあればBusyCompositionで拒否。Commit/Cancelの完了後に呼出側が明示的に再実行する。自動切替は行わない |

previewは変換済み `out + pending` を偽preeditへ表示する。Commitではpendingが空であることを追加検査し、outを本文の末尾へ追記する。空Textは成功した値として扱い、既存の確定済み本文を削除しない。NoOutput・欠けた出力・Text以外・不正Packet・変換失敗は文書へ適用しない。失敗時に以前のpreeditが残っても、新入力の成功結果を得たことにはしない。

最初のReplaceInputで未確定セッションを作り、その計画版を固定する。空入力へ置換してもセッションは自動終了せず、明示Commit/Cancelまで計画切替を拒否する。InputMode::Finalizeは変換規則であり、文書への確定とは別段階。結果の生成・受取・適用を分離して、この違いを検査する。

## 遅延・重複・文書失敗

Engineは同期のまま。呼出側が生成済みResponseを保持してからreceiveすることで、送達の遅延・順序逆転・重複を模擬する。実際の非同期Engineや送信キューを実装したわけではない。

NoOutput・欠けた出力・不正Packet・識別情報の不整合は、一部のテストで生成済み結果へ注入して配信境界の拒否を確認する。既存Nodeの実装やEngineの出力検査を無効にする変更は行っていない。通常の変換失敗は、実用ローマ字ノードのunknown=error設定を実際に実行して検査する。

成功した文書適用で要求を消費するため、同じ結果の再適用や同じCommitの二重確定はできない。未確定セッションが終わった後のCommitはNoCompositionとなる。再試行前に入力が変われば古い確定結果は拒否する。新しいセッションで同じ文章を入力しても、以前の結果を再利用しない。

**偽文書の失敗は「本文・preedit・文書stampが全て未変更」と確定する原子的な失敗だけ**をモデルにしている。この前提では受取済み結果を保持して安全に再試行できる。確定成功前に入力を捨てず、成功後は一度だけ消費する。取消の文書操作が失敗した場合も入力は保持するが、その前の確定要求は無効にする。

試験用の外部文書変更はstampを進めて古い結果を拒否する。ホストの入力は残し、明示Cancelでホスト状態を片付けてから新しい入力を始める。偽文書にそのセッションのpreeditがなければ、Cancelは文書を書き換えずホスト入力だけを捨てる。この所有IDのモデルを実際の文書rangeの安全性と同一視しない。

## 検査する内容

- `k/ky/kya`、`n`のcompose/finalize、全文を短くする置換、空入力・数字・記号・Unicode。
- 結果生成後・受取後にも本文が未変更であることと、明示した適用成功による一度だけの確定。
- 入力更新・文書改訂・コンテキスト切替・計画変更・セッション終了で古い応答を拒否し、重複が現在の結果を消さないこと。
- 変換失敗、NoOutput、不正出力、非空pendingを持つ確定結果を文書削除へ解釈しないこと。
- preview/Commit/Cancelの原子的失敗、入力保持、再試行、再試行前の入力変更、二重確定の拒否。
- 未確定中のprepare、activate/rollbackの拒否、明示終了後の切替と復帰、prepare失敗で稼働結果が変わらないこと。

## 制限と次工程

TSFの編集セッション、HRESULT、アプリ側の文書範囲、フォーカス喪失、外部composition終了、結果が不明な失敗からの回復は検証していない。実TSFで書込みが成功したか不明な場合、この偽物と同じ再試行をすると二重確定を起こし得る。実ホストの失敗・再試行ポリシーは別の採用判断と検査が必要。

任意位置編集・選択範囲・キャレット・書記素分割・キー割当・入力の削除単位・候補UIは未実装。本文末尾への追記と、自分の偽preeditの全体置換だけを扱う。[UTF-8/UTF-16境界実験](windows-text-boundaries.md)とは独立しており、sourceSpanを文書位置へ変換しない。

ホスト内の位置・世代・命令・エラーはexampleの非公開型で、正式APIとして公開していない。標準RuntimeInputの4096コードポイントと安全整数の検査を使うが、この偽物の本文蓄積や配信待ちResponseへ製品用の容量・遅延上限は設けていない。実ホストへ接続する前に資源上限と寿命を決める。

次はこの状態機械をレビューし、制御できる編集欄・TSFの文書変更/失敗/フォーカスを別の実験で確認する。OS登録・SDK/COM依存の導入は本PRでは行わない。
