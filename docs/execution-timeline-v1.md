# 実行タイムライン v1

親Issue #306。第1段階 #307 / PR #308 はCore記録基盤。第2段階 #309 は配布アプリのWasm実行に、グラフ下部の横棒・右側詳細と独立診断APIを接続する。legacy/async検査用画面の未対応計測は表示しない。

## 表示契約

横軸はms。各工程の開始・終了を横棒で示す。結果準備、利用者への初回応答、処理の実終了を区別する。Coreの `core-result-ready` を画面の「初回応答」と呼ばない。遅い処理が残る場合、その棒を継続する。選択すると右側に時刻、状態、識別番号、計測元を展開する。格ゲーのような比較と経過の把握に使うが、フレーム数への換算はしない。

## Core API（第1段階）

`ExecutionController` / `RunLedger` の別診断API：

- `start_trace()`：新しい記録を開始し、前の記録を置き換える。既定OFF。
- `read_trace(after, limit)`：シーケンス番号より後を最大256件取得。1〜256件以外は拒否。
- `stop_trace()`：記録を停止し、経過時間と残存記録を固定する。実行は停止しない。
- `clear_trace()`：記録を停止し、当該セッションの記録を消す。再開しない。

`RunSnapshot` とprotocol 3の正式なJSON形式は変更しない。診断は実行、取消、結果採用、資源上限の判定に使わない。失敗・取りこぼしは実行結果へ伝播しない。

記録開始後に新しく受理したrunだけを対象とする。開始前からのrun、同じstartKeyの再取得には開始イベントを捏造しない。途中から記録した場合に、開始前の状況まで分かったように表示しない。

## 計測点と時計

Core内の単調時計を使い、記録開始からのµsを10進文字列で保持する。画面ではmsへ換算する。CPU時間ではない。別プロセス・ブラウザの時計はまだ統合しない。

記録するのは、run受理、要求範囲内ノードの依存待ち、実行可能状態、実際の呼出開始、結果の検証・適用、取消、取消後の停滞、認証された呼出終了、Coreの結果準備／NoOutput／取消／期限切れ／失敗／完了、全処理の終了確認。

`call-ended` はCompletionPermitとstart復帰の両方をCoreが確認し、処理の所有資源を解放した後。Worker OSプロセスの終了を意味しない。`physical-ended` はDispatcherが実際の残存数ゼロを確認した時点。論理結果時点の古い残存数から推測しない。直接RunLedgerだけを利用する呼出者にはDispatcherの終了確認は存在しない。

## 保存内容・隔離

記録ごとに新しいランダムな記録IDを作り、input/run/plan/node/callを記録内の別名へ置換する。raw RunKey、入力・出力本文と長さとハッシュ、設定、診断の自由文、URL、パス、秘密情報は保存しない。ノード種別と版は宣言から取得し、種別の表示は128文字以内とする。入力revisionなどの照合値は非公開の有界索引だけに置き、JSONへ出さない。

各Sessionが独立した記録領域を持つ。別Sessionの混雑は相互に影響しない。通知側はtry_lockで待たず、競合時には診断だけを落としてdroppedを増やす。記録OFF時はイベント生成・時刻取得・整形を行わない。通知のTicketは弱参照と世代番号を持ち、停止・消去・新記録開始・Session破棄後の古い通知で記録を復活させない。

## 有界保存と欠落

最大20,000イベント、シリアライズしたイベント列8MiB以内（外枠用4KiBを予約）、200run、60秒。呼出索引も最大20,000件。満杯では終了済みrunから置き換え、可能なら実行中runを残す。全runが実行中なら新規診断だけを落とす。古いイベント・容量超過・件数超過・ロック競合はdroppedに反映する。欠落を完了として描かない。

取得はページ単位。状態を取得しただけでrunを再実行しない。実行終了から時刻を再構成しない。本文入り通常ログへのフォールバックはしない。

## 配布アプリで使う（第2段階）

1. 「実行結果」で実行Hostへ接続し、グラフを確認・承認する。
2. グラフ下部の「実行タイムライン」で「記録を開始」。記録は既定OFF。
3. 実行結果タブでグラフを実行し、タイムラインへ戻る。タブを変えても記録は継続する。
4. 工程の棒を選ぶと右側に時刻・状態変化・番号・計測元を表示する。ms軸は実行受理からの経過。数字は記録内の別名。
5. 「ライブをA/Bに固定」は表示の保存だけで、記録や実行を止めない。A/B比較は各実行の起点をそろえた独立した図。別記録の同じ番号を同じNodeと自動判定しない。
6. 「表示記録を保存」でJSONを手動保存。「A/Bへ読込」は表示専用。読込だけで接続・承認・実行・再実行・記録開始を行わない。

青は呼出中または終了確認待ち、緑は呼出の終了確認済み。待機と結果確定を別に描く。開始や終了の欠落は模様・未取得の表示にし、結果が返っただけで未終了の棒を閉じない。個別呼出の終了はWorker OSプロセスの終了時刻ではない。100工程ごとにページを切り替えられる。

「初回応答」は `host-response-published`。現在も有効なComplete/Recovered結果について、Hostが制限内の成功応答をstdoutへ送り、改行とflushに成功した後にだけ記録する。Core結果準備・ブラウザー描画・TSF反映とは区別する。最初の公開通知を落とした場合、後の再取得を初回と記録しない。新しいrunは測定を継続できる。起点を取得できなかった記録は最初の取得イベントを表示起点と明示する。

停止は記録と経過時間を固定するだけ。消去と保護は記録を止めて消す。保護は操作中の一時的なController cloneが残っていてもCore記録を明示消去し、画面のライブ・固定両方を消す。古い通信・選択中のファイル・読込中のファイルからの復活を防ぐ。保護解除後は記録を自動再開しない。通常のSession切替ではライブだけを消し、明示固定したメタデータは比較用に保持する。

ライブ8MiB・20,000件・200run・60秒、固定はA/Bの2件（各8MiB）。手動JSONは転送16MiB以内、解析後の記録8MiB以内・20,000イベント・200run。未知のプロパティ、本文や任意エラーを付けたレコード、不正な時刻・別名の不整合・異なる呼出への同じ番号の使用を拒否する。読込ファイルは「読込・表示専用」と表示する。既に保存したファイルは保護時に自動削除しない。

## 外部Hostの別診断操作

外側の信頼済みHost操作にだけ `traceStart {}` / `traceRead {after,limit}` / `traceStop {}` / `traceClear {}` を追加する。返却は `{trace: TraceSnapshot}` のみ。`after` は先頭ゼロのないu64十進文字列（初回は `"0"`）、limitは1〜256。承認済みSessionと既存の保護・失効確認を必要とし、生のControllerを公開しない。正式protocol3の要求・RunSnapshot形式・guest応答形式には混ぜない。

## 負荷の検査

配布版の検査スクリプトを同一バイナリで `--trace 0` / `--trace 1` として実行する。ONはCore基本記録と150ms間隔のページ取得を含む。ブラウザーの描画処理は含まない。初回・warmupを除き、同じ6入力を順番に回し、出力一致と全physical countsゼロを確認した100回のP95を、順番を入れ替えた3組で比較する。目標は5%以内。一台での結果を他の端末の速度保証とはしない。

第3段階のHost/Wasm/broker内部工程・起動／再起動の詳細、第4段階のNode自己申告span、第5段階の実TSF経路は、この基本画面の完了とは別に扱う。

## 第3段階のHost区間（#315）

基本の「記録を開始」は従来どおり。明示的な「詳細記録を開始」は基本イベントに加えて、承認済みの新規Wasm呼出について以下の開始/退出を右側詳細へ時刻付きで記録する。HostとCoreは同じSession記録の単調時計を使い、別プロセスの時計は合成しない。

| イベント接頭辞 | 実際に囲む区間 |
| --- | --- |
| `host-request` | Hostの設定/実行許可確認、要求・辞書payload・ネットワークscopeの準備。Core prepareやインストール時の検査は含まない |
| `worker-staging` | 実行要求のJSON化、AppContainer、コードsnapshot/ACLとJobの準備 |
| `worker-process` | プロセス作成の試行、pipe通信、実行待機、終了回収。実プロセスの起動完了時刻や純Wasm実行時間ではない |
| `worker-cleanup` | 回収後のJob/ACL/profileの後片付け、結果検査・出力の取り出し |
| `broker-exchange` | ネットワークcontinuationのHost側交換。権限/取消検査・通信を含み、URL、本文、秘密、サイズ、自由文は記録しない |

各区間の `-finished` はHostのスコープ退出であり、成功の判定ではない。途中エラーやunwindでも退出する。実終了と成功は既存のCoreイベント/実終了確認と区別する。準備途中で失敗した場合に後続区間を捏造しない。continuationごとに新しいWorker呼出の区間が現れるが、WorkerのPID/OS起動完了/再起動世代を報告するものではない。終了や開始が記録から落ちた区間の長さを推測しない。

追加診断操作は `traceStartDetailed {}`。既存 `traceStart {}` は基本記録のまま。どちらも新しい記録世代で履歴を置き換え、同じ許可・保護・失効確認を経る。詳細OFF時は区間の時計取得・文字列化・イベント生成を行わない。停止・消去・保護・再開始後の古い区間は弱参照と記録世代で拒否し、実行を止めたり再開したりしない。診断の呼出はゲストへ公開しない。

正式protocol3、RunSnapshot、固定SDK v1、公式パッケージのbytesは変更しない。JSONの本文なしスキーマと容量上限を維持し、詳細イベントを追加許可する。新しい画面は旧基本記録を読み込める。旧画面は未知の詳細イベントを含むJSONを拒否するため、詳細記録の比較には対応する画面を使う。

これは第3段階の最初の単位。Worker内部のWasm compile/instantiate/execute、実起動/再起動、配布版の詳細OFF/ON負荷比較は未完了であり、計測だけで高速化を主張しない。TSF/OS登録/実キー入力は扱わない。

### 配布版での詳細記録の負荷比較（#319）

`scripts/benchmark-windows-application.mjs BUILT_FOLDER --trace 0|1|2` の0はOFF、1は基本、2はHost詳細。詳細は `traceStartDetailed` に対応する配布版を明示的に使い、古いHostへ基本記録として再試行しない。レポートの `diagnostics.mode` は `off` / `basic` / `host-detailed` を区別し、Host区間の開始件数・取得件数・droppedを報告する。最後の実終了後に記録を停止し、残りの診断ページをサンプル測定区間外で回収する。

比較には同一の検証済みバイナリを使い、各モードのfirst run/warmupを除いた100回を順番を入れ替えて3組測る。manifest/Worker/module/graph/dictionaryのhashと環境が同一かを確認する。基本記録のP95増分5%目標と、詳細記録の実測結果を混同しない。小さな同梱グラフの結果は実用規模辞書・Reference IME・ブラウザー描画・TSFの速度保証ではない。

### Worker内部の相対区間（#321）

詳細モードでは、検証済みの信頼側Workerへだけ独立した匿名pipeの書込handleを渡す。標準出力・標準エラーのguest応答経路とは分離し、SDK v1や公式packageのbytesは変更しない。通常/基本モードでは追加handle・reader thread・Worker時計を作らない。診断pipeの準備/reader/構文に失敗しても変換の成否を変えず、少なくとも1件の診断欠落としてdroppedへ反映する。AppContainer・Job・実終了確認を省略するfallbackはない。

Workerは固定12区間の開始/退出だけを記録する。計測対象全体、DLL読込、module読込、stdin読込、Engine/Store準備、compile、instantiate、ゲスト呼出準備、diyime_call、応答の取出し、stdoutの送信/flush、Runtime後片付け。入力サイズや本文・出力・設定・path・自由文は含めない。最大24個の固定長frameと8-byte版ヘッダー（248 bytes）で、4096-byte pipe bufferを満たさない。Parent側も4096 bytesに制限し、超過分は保存せずEOFまで排出する。診断EOFは処理完了の証明にならず、OS process handleの終了確認後にreaderをjoinしてから既存の実終了所有権を返す。

取得する `worker-interval` の `atUs` は**Hostが受信記録を採用した時刻**。`worker: {instance, phase, startedUs, finishedUs?}` はWorker自身の単調時計を起点としたµs文字列であり、Hostの時間軸に足し合わせない。Worker時計の起点は隔離確認と引数解析を終えた計測開始で、OSプロセスの生成時刻/初期化完了ではない。実終了後に右側の「Worker内部（相対時刻）」へ専用の棒と開始/退出/所要msを表示する。未退出は所要時間を補間せず「退出未取得」とする。正常なscope退出も成功やOS終了を意味しない。

instanceはHostが当該run/Node内の呼出順に付ける1〜20,000の記録内番号で、PIDやhandleではない。continuationごとの新規processを区別し、別runの同じ番号を同一processとは扱わない。未知phase、重複、逆行、開始のない退出、余分なframe、部分frameを拒否し、取消等で開始だけが残った区間は未完のまま保持する。停止・消去・保護・新しい記録開始で旧ticketは無効となる。ゲスト自己申告の内部工程は含めない。

OS起動の完了時刻、実再起動/再利用方式、SDK v2の自己申告工程、正式な3組×100回の負荷比較と速度改善は、この実装から達成したと推定しない。これらとTSF接続を別の工程として追跡する。

### 工程別の集計（#323）

配布ベンチマークの `diagnostics.phaseSummary` は取得したHost/Worker区間を別々に集計する。工程ごとの `completed` / `incomplete`、退出を取得できた区間の `totalUs` / `minUs` / `maxUs` をµs十進文字列で返す。退出未取得しかなければ時間のフィールドを省略し、0秒の工程と区別する。Workerは自身の開始/退出差だけを使い、Host受信時刻との差を時間にしない。Workerの全体区間と子工程を加算して経過時間や比率と呼ばない。

Hostの開始/退出はrun/Node/工程で照合する。dropped、重複開始、開始のない退出、最終回収後にも残る開始があれば `hostCoverage: incomplete` とし、不確かな対から作った集計を残さない。Workerの各区間は `received-intervals-only` と明示し、欠落時に全実行を取得したとは扱わない。OFF/basicで取得しないHost内部工程は `disabled` になる。本文や任意の工程名を受け入れない。

長時間の比較には `--progress-every 10` 等を指定できる。完了したサンプル件数とモードだけを測定区間外でstderrへ出し、stdoutの結果JSONへ混ぜない。集計や進捗機能は性能改善そのものではない。

長い比較でもCoreの60秒/件数/容量制限は広げない。各runの測定開始前に新しい記録を開始し、実終了を確認して測定時間を確定した後に停止・全ページ回収する。first run/warmupも同じ規則とし、各記録を別のprofilerで照合した完成集計だけを合算する。記録ID・run/Node/Worker番号を別世代の開始/退出の組に使わない。`diagnostics.recordings` は記録回数、`dropped` は記録ごとの欠落数の合計。記録操作と最終回収はサンプル所要時間に含めず、実行中の150ms取得は含める。この測定方式を旧方式と同一の観測負荷とは呼ばない。
