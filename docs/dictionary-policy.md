# DIY_IME2 — 辞書の取り扱い・拡張方針

- 状態: **設計方針と候補の整理**。辞書フォーマット・検索APIの詳細は未決定。
- 対象: 文章変換・かな漢字変換・形態素解析・将来の学習／ユーザー辞書。
- 関連: [コア設計仕様](core-architecture-v0.1.md) / [初期E2E実装](initial-e2e.md) / [Issue #1](https://github.com/pitapa79/DIY_IME2/issues/1)
- 次の検討資料: [最初の辞書ノードの仕様案 v0.1](dictionary-node-proposal-v0.1.md)（Issue #15で限定採用。正式Node・Host APIは#206〜#208で実装）。

## 1. 基本方針

**DIY_IME2本体は特定の辞書形式を必須にしない。**

- **辞書データ**（ファイル・DB・外部サービス）と、**読み込み／検索／候補生成を行うノード**、**候補評価／選択ノード**は別の責務とする。
- 辞書の解釈、索引、検索戦略、候補生成やフォールバックなどの意味的処理は、原則としてノードまたはノードが利用するライブラリの責務とする。「ノードで解決できることはノードで解決する」という原則を維持する。
- ノードは、読み込んだ辞書固有の表現を、文章変換ポート上では既存の `Packet`（Text / Sequence / Choice）に変換して次段へ渡せる。辞書ファイルそのものを共通Packetの形式に揃える必要はない。
- 同じグラフ上で異なる辞書由来のノードを併用することを妨げない。ただし、辞書形式間の互換性・自動変換・検索APIの統一を現時点で保証しない。
- **「辞書ファイルは独立したデータ／リソース、辞書を使う処理はノード」**を基本の整理とする。将来の共有キャッシュや辞書管理画面などは必要性を検討して別途設計する。
- ランタイムのポート規格と辞書ファイルの保存・配布形式は別の問題である。

## 2. 世の中の辞書／形式の参考例

以下は**調査・接続候補**であり、採用または同梱を決定するものではない。入力データ・付属ファイル・コンパイル済み辞書の細部は各プロジェクトの仕様に従う。

| 例 | データの性格・形式の例 | 想定する利用 |
| --- | --- | --- |
| SKK辞書 | 読みと候補のテキスト記法 | 単語のかな漢字候補、簡易な入力方式 |
| Mozcの辞書資産 | TSV系の語彙データや独自コンパイル済み辞書等 | かな漢字変換の語彙・コスト・接続情報の研究 |
| MeCab / IPADIC | 語彙CSV、品詞・連接情報、コンパイル済み辞書 | 形態素解析、単語分割 |
| UniDic | 形態素解析向けの豊富な語彙・品詞情報 | 読み・語彙分析 |
| SudachiDict | CSV系の開発用データと専用辞書形式 | 分割・正規化・形態素解析 |
| Rime | `.dict.yaml` 等の入力コードと語彙の辞書 | 独自入力方式・多言語入力 |
| JMdict | XML形式の読み・表記・語義情報 | 語義参照、翻訳・補助情報 |

**注意:** 形態素解析用辞書を、そのままかな漢字変換用辞書として置き換えられるとは限らない。品詞体系・左右文脈ID・接続コスト・語彙単位・読みの扱いが辞書ごとに異なる。

## 3. 保存形式・実行形式の候補

| 形式 | 想定用途 | 注意点 |
| --- | --- | --- |
| TSV / CSV | 小規模テスト辞書、テキストでの編集・取り込み | 大規模検索には索引が必要な場合がある |
| JSON / YAML | 小規模な構造化辞書、設定、メタデータ | 大規模な全件読み込みは重くなりやすい |
| SQLite | ユーザー辞書、追加・削除・検索、学習履歴 | スキーマと更新整合性が必要 |
| Trie / FST 等の索引・バイナリ | 大規模・低遅延検索 | ビルド・互換性・更新方式の設計が必要 |
| 外部API／サービス | オンライン辞書・特殊分野・LLM連携 | ネットワーク、遅延、権限、可用性の考慮が必要 |

**配布用の原本と実行時の高速な索引は分けられる。** たとえばTSVから索引を作ることは可能だが、それをDIY_IME2の共通仕様として強制しない。

## 4. 初期テストと段階的な拡張

### 現時点ですでに存在する実装（新しい採用判断ではない）

[Issue #1](https://github.com/pitapa79/DIY_IME2/issues/1) の7段階のE2Eは**実装済み**。辞書部分は `src/builtins/initial_e2e.rs` にある**固定規則・小辞書**による試作用。既存の `e2e.*` ノード、JSONグラフ、期待結果は変更しない。

### 次の段階の候補: 外部TSVを読む辞書ノード

初期の独立した辞書ファイルを試す場合は、次のような**DIY_IME2用のテストTSV案**が扱いやすい。

```tsv
reading	surface	weight
ほんじつ	本日	100
ほんじつ	本実	20
こうすいかくりつ	降水確率	100
こうすい	降水	90
こうすい	香水	30
かくりつ	確率	90
かくりつ	確立	40
```

- **このTSVは提案サンプルであり、既存の `e2e.*` ノードが現在読み込むファイル形式ではない。** 新規実装・移行は別タスクで判断する。
- `weight` は提案上の**候補の優先度**であって確率ではない。実際のスコア採用・変更・正規化はノード側の定義に従う。
- 読みの一致、複数候補、数字や記号の保存、未知語の扱い、同点時の優先順位、再現性などを小さな固定データで検証する。
- 必要なら読込エラー、ファイル未存在、不正行、文字コード、重複キーのテストも追加する。
- **Node API・設定スキーマ・TSVの正式なカラム仕様・辞書検索API・外部ファイルのパス解決方法はまだ決めない。**

### その後の候補（優先順位・採否未決定）

1. SKK辞書を利用した検索ノード／インポーターで、実在する辞書の取扱いと探索性能を検証。
2. Mozc・MeCab/IPADIC・SudachiDict等の語彙・形態素・接続情報を研究し、全文変換に必要な解析・評価方式を検討。
3. 必要に応じてユーザー辞書、学習履歴、複数辞書の優先順位、更新・キャッシュ・共有を検討。

これは**検討の順番の案**であり、上記辞書の採用・同梱・対応を約束しない。

## 5. スコアの意味を混同しない

- DIY_IME2の現在のChoiceは**同一Choice内で高い数値ほど優先**。Choice間のスコア比較や確率解釈は保証していない。
- 一方、形態素解析辞書などの**コスト**は「低いほどよい」定義の場合がある。また、頻度・重み・コストの尺度も辞書によって異なる。
- 辞書から得た値をそのままChoiceのスコアに流用しない。対応する変換／候補生成ノードが、**向き・尺度・比較可能な範囲・未指定時の扱い**を定義する。
- 辞書統合時も単純な加算や一律の百分率化を本体が暗黙に行わない。

## 6. 配布・ライセンス・更新の留意点

- **辞書とプログラムは別々にライセンスを検証**する。著作権、再配布、改変、表示義務、辞書の元データに含まれる別ライセンスを確認する。
- 辞書ごとに出典、ライセンス、入手先、版、ハッシュ、改変の有無等を記録する方法を将来検討する。**辞書が公開されていることは再配布許可と同義ではない。**
- 辞書の更新とグラフ実行計画の切替は区別する。更新途中の破損した辞書や異なる版のデータが、同一の実行へ混在しないことが望ましい。辞書のスナップショットや版管理、キャッシュの無効化は後続設計。
- 大規模辞書のメモリ消費、読み込み時間、検索遅延は**測定してから**索引方式を決定する。
- 個人辞書や入力履歴にはプライバシー上の配慮が必要。永続化・削除・同期・権限は後続設計。

## 7. 今回は決めないこと

- DIY_IME2における唯一の辞書形式、正式な標準辞書、辞書の同梱有無。
- 外部辞書のロードAPI、ノード種類、辞書インターフェースとリソースの共有単位。
- 辞書ごとのスコア換算、形態素コストの利用法、学習アルゴリズム。
- ユーザー辞書のデータベース、GUI、エクスポート・インポート、配布・更新機構。

> **結論:** 特定の辞書形式に本体を固定せず、辞書を扱うノードが形式に応じて検索・候補生成する。まず既存E2Eの安定動作を維持し、外部TSV・SKK等の対応は個別の実装タスクで判断する。
