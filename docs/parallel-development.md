# 並行開発とworktreeの運用

共通の承認・マージ・AI自主着手条件は[開発ガバナンス v1.1](development-governance.md)を正本とし、AIの具体的な安全ルールは[AGENTS.md](../AGENTS.md)を参照する。この文書は、同時並行開発の作業場所と引継ぎ手順に限定する。

## タスクと作業場所

- 原則 `1タスク = 1 Issue = 1専用ブランチ/worktree = 1 PR`。巨大なタスクはレビュー可能な独立単位へ分ける。
- 作業担当は現在の `DIY_IME` のIssue、依存PR、mainの完全SHAを確認する。旧 `DIY_IME2` のSHAやIssue番号は使い回さない。
- 同じPCで並行実装する場合、担当ごとに専用worktreeを作り、同じ作業フォルダーで互いのブランチを切り替えない。
- 別PC・クラウドの別cloneも利用できる。ビルド出力・開発サーバーのポート・一時生成物の競合に注意する。
- 他担当のprocess、worktree、未コミット差分を停止・削除・resetしない。
- 依存関係がある場合はIssue/PRで明示し、承認済みの共通変更を先に取り込む。担当外の改修を勝手に取り込まない。

## 本体とNode側の連携

本体はCore、system、Windows/TSF、Host/Worker/broker、権限、Editor、配布。処理Node側は変換・辞書・候補評価の実装・検査・パッケージ。Nodeで本体APIの変更が必要な場合は、本体Issueで承認・契約変更・検査を行い、その後別のNode側Issue/PRで固定SDKへ反映する。

Node側を担当するAIは、本体の過去の `src/nodes/<name>/` 実装ガイドを現在の本体の所有ファイルと誤認しない。

## PR・引継ぎ

- 作業を開始したら対象Issueへ開始SHAと担当PRを記録する。
- 早い段階でDraft PRを作り、依存・テスト・未完了範囲を共有する。
- PRに `Refs #番号`、完成時のみ `Closes #番号` を使う。
- 引継ぎでは `Issue / PR / branch / HEAD SHA / 変更内容 / 成功・失敗した検査 / 残作業 / 依存PR` を記載する。
- 同じタスクの再開は既存PRと引継ぎSHAから行い、未完了の差分を新規mainからの作業で上書きしない。
- マージ可否は[ガバナンスのLevel分類](development-governance.md#5-変更レベルとマージ権限)による。Level 1・2は必要なCI/検査と自己点検を満たせばAIがマージ可能。独立レビューは原則任意だが、必要と判断・指定されたレビューが未完了ならマージしない。Level 3はメンテナー承認必須。

旧リポジトリの初期タスクやエージェントの担当履歴は[移行記録](migration.md)の方針に従い旧 `DIY_IME2` で保存する。
