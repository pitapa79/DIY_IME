# 並行開発と作業分担

この文書は、現在の `DIY_IME` 本体リポジトリにおける作業方法を示します。旧 `DIY_IME2` の初期タスク・過去のブランチ・担当記録は[移行記録](migration.md)に示す旧リポジトリへ保存し、ここでは現在も必要な運用ルールだけを扱います。

エージェントの詳細な制約は[AGENTS.md](../AGENTS.md)を正本とします。設計上の判断は[設計思想](design-philosophy.md)を参照してください。

## 基本の作業単位

- 原則として **1タスク = 1 Issue = 1専用ブランチ/worktree = 1 PR**。
- Issueには目的・採用済み要件・受け入れ条件・対象外・依存関係を記載する。
- AIは改善Issueを提案できるが、**未承認の機能や仕様の実装を独断で開始しない**。機能採否はメンテナーが決める。
- 開始時に現在の `main` の完全SHAを記録する。旧リポジトリのコミットやIssue番号を新タスクの基準に流用しない。
- 担当が異なる場合、同じ作業フォルダーを共有せず、別のworktreeまたはcloneを使う。

## 本体と処理Nodeの分担

- **本体リポジトリ**: Node非依存Core、systemノード、Windows/TSF境界、Host/Worker、権限broker、エディター、配布・診断。
- **処理Node側**: 変換、辞書、候補評価などのNode実装・テスト・パッケージ。
- 本体のAPI変更が必要なら本体側にIssueを作り、承認済みの契約変更として実施する。Node側に固定snapshotとして取り込む作業は別Issue/PRとする。
- テスト専用の合成Nodeを公式の配布用Nodeと混同しない。

## PRと検証

1. 依頼された変更範囲を確認し、必要な担当検査を追加・実行する。
2. 正式なfixtureや安全境界、互換性を弱めてテストを通さない。
3. Rustの変更は原則 `cargo test --locked`、`cargo fmt --all -- --check`、`cargo clippy --locked --all-targets -- -D warnings` を確認する。
4. UI/bridgeの変更は `editor/` のテスト・ビルドも確認する。Windowsの実行/隔離に関する変更は、該当する実Windows検証が必要。
5. PRに担当Issue、開始SHA、変更点、成功した検査、未検証の環境・条件、セキュリティ・互換性への影響を記録する。
6. 最終受け入れ条件を満たしたPRだけ `Closes #番号` を使い、途中の依存PRは `Refs #番号` とする。
7. 他担当のブランチ・作業ファイルを暗黙にマージしたり、停止・削除したりしない。

## 履歴の扱い

旧リポジトリにある過去のタスク・試験・担当引継ぎは、当時の記録です。**新しいリポジトリに存在するIssueだけを現在の作業指示として扱います。** 継続が必要な未完了タスクは、受け入れ条件と現在の実装を再確認してから新しいIssueとして作成します。

旧成果物を参考にする場合も、旧mainに対するテスト成功を現在のmainの検証完了と読み替えないでください。
