# DIY_IME 開発ガバナンス v1.2

状態: メンテナー承認済み。新しい `pitapa79/DIY_IME` の作業に適用する。

## 1. 権限と基本方針

- **利用者から見た製品仕様、機能採否、利用者に許可する能力、安全性についての約束、公開・配布方針の最終決定はメンテナーが行う。**
- **実装方式、内部アーキテクチャ、アルゴリズム、プロセス管理、既存の安全要求を満たすためのセキュリティ技術は原則AIが判断する。** メンテナーに技術審査を要求しない。
- AIは既存仕様を守るバグ修正、保守、検査・文書改善を自律的に提案・実施できる。
- AIはIssue・ブランチ・PRの作成、検査、自己点検、条件付きマージを行える。独立レビューはリスクに応じて追加する。Claudeなど特定サービスの利用を前提にしない。
- **利用者に提供する機能・体験・権限・安全保証の変更には事前承認が必要。** 内部実装の変更は、それらを維持する限り原則AIに委任する。IssueやPRを作っただけでは承認にならない。
- 外部からは当面、Issueでの提案・不具合報告・検証情報を中心に受け付ける。

技術的な現行仕様・互換性・安全境界は、[設計思想](design-philosophy.md)、[API/契約](core-architecture-v0.1.md)、正式fixture、[セキュリティ資料](security/)と実装に照らして判断する。古い `DIY_IME2` のIssue番号や記録を新たな実装許可にしない。

## 2. Issueの分類と自主着手

| 種類 | 対象 | AIの自主着手 |
| --- | --- | --- |
| Bug | 既存の合意済み仕様に反する動作 | 可 |
| Maintenance | 動作を変えない保守、内部整理、依存更新 | 条件付き |
| Documentation | 既存の仕様に沿う訂正・案内 | 可 |
| Test | 既存契約のテスト補完 | 可 |
| Performance | 同一動作・同一安全性の性能改善 | 条件付き |
| Feature | 新しい機能・能力・入力方式 | 事前承認必須 |
| Specification | 利用者向け動作・公開契約・互換性方針の変更 | 事前承認必須 |
| Internal Engineering | 既存仕様・安全要求を維持する内部方式・構造・アルゴリズムの変更 | 条件付き可 |
| Security Policy | 許可される能力、利用者に約束する保護水準、信頼境界の保証の変更 | 事前承認必須 |
| Security Implementation | 同じ保護水準を維持・改善する隔離・権限検査・Worker管理等の実装変更 | 条件付き可 |

AIはIssueを提案・起票できるが、それ自体は着手・仕様承認を意味しない。自律着手する場合は、既存の根拠、目的、変更範囲、受け入れ条件、対象外、依存関係を記録する。分類が曖昧な場合は高い承認レベルで扱い、勝手に仕様を補わない。

既存仕様を修復するための新しい内部コードやセキュリティ実装方式の変更は、必ずしもFeature・Security Policyではない。ただし利用者に新しい能力を提供したり、既存保証・権限範囲を変更する場合は承認が必要。

自主着手できることと自動マージできることは別の権限である。

## 3. 判断責任の分担と承認

### メンテナーが決めること

利用者が何をできるか、入力・候補・取消などの体験、外部Nodeにどの能力を許すか、パスワード保護や隔離について利用者へどの保護を約束するか、公開・配布・ライセンス・費用負担などを決定する。**実装手法の選択や専門的な技術審査はメンテナーへ求めない。**

### AIが決めること

既存要求を満たす内部データ構造、アルゴリズム、非同期制御、Worker終了方法、Wasm/AppContainer等の隔離の実装方式、ライブラリ選定、セキュリティの修正方法、実装上の検証方法を原則AIが決める。選択理由・代替案・確認した保証をIssue/PRに記録する。

技術的な不明点はAIが調査し、必要なら検証コード・テスト・比較を実施する。安全性や互換性を十分に実証できない場合、**変更をマージせず、技術的ブロッカーとして記録して調査を継続する**。メンテナーに『どの内部方式が正しいか』という未整理の二択を押し付けない。利用者体験・保証・費用などメンテナー自身の方針決定が本当に必要な場合のみ、選択肢と利用者側への影響を整理して質問する。

技術判断の委任は安全性の保証を意味しない。テスト、境界条件、失敗時の扱いを検証し、確証のない重大なリスクは未解決として扱う。

### 事前承認が必要な変更

次はメンテナーの事前承認が必要。

1. 新機能、新Node能力、新入力方式の採用
2. 利用者やNode開発者への公開API、データ・Node契約、互換性方針の**外部から観測される変更**（既存契約を守る内部実装変更は委任対象）
3. 許可する能力・権限範囲、隔離・保護入力等について**利用者へ約束する安全水準や信頼境界の保証を変える変更**（保証を維持する技術的な実装変更は委任対象）
4. 対応OS、配布形態、ライセンス、公開範囲の変更
5. CoreとNodeの**公開された責務や利用者が構成できる範囲**の変更（内部の責務分割・モジュール設計は委任対象）
6. 将来の利用者の構成自由度に影響する設計上の選択
7. 本ガバナンスとAIの権限の変更

承認内容と範囲はIssueまたはPRに追跡可能な形で記録する。承認対象外の拡張は再承認を必要とする。AIが自身の権限を拡大する変更を自動承認・自動マージすることは禁止する。

## 4. ブランチ・Issue・PR

原則 `1タスク = 1 Issue = 1専用ブランチ/worktree = 1 PR`。

- 作業開始時は**現在のDIY_IMEのmain**の完全SHAを記録する。再開時は既存PRと作業SHAを優先する。
- Issueに目的、受け入れ条件、変更範囲、対象外、依存関係を記載する。
- 異なる担当は別worktree/cloneを使い、他担当の未完了作業を上書き・停止しない。
- PRに対応Issue、変更点、検査結果、未検証範囲、互換性・セキュリティ影響を記載する。
- 途中の依存PRには `Refs #番号`、条件を満たす最終PRのみ `Closes #番号` を使う。
- マージ後の作業ブランチは原則削除する。追加修正は新しいタスクにする。

## 5. 変更レベルとマージ権限

変更は**内容と影響**で分類する。ファイル数や差分行数のみで判定しない。混在する場合は最も高いレベルを適用する。

### Level 1: 通常変更

既存仕様を変えず、影響が限定的な文書訂正、軽微なバグ修正、テスト追加、局所的整理など。

**共通条件を満たす場合、AIによるマージを許可する。**

### Level 2: 影響確認が必要な変更

大規模整理、性能最適化、依存更新、Coreの実行制御、隔離方式・権限検査・Worker管理の内部変更、UI広域変更など、**利用者体験・公開契約・安全保証を維持**するが影響確認が難しいもの。

既存仕様・セキュリティ保証の範囲内であれば、**自己点検、該当テストとCI、安全性・互換性の根拠、影響範囲の記録を条件にAIによるマージを許可する**。内部技術の不確実性が大きい場合は追加検証・レビューを実施し、解消しなければ技術的ブロッカーとして保留する。技術的な採否だけをメンテナーに委ねない。Level 3に該当する内容はこの権限に含まれない。

### Level 3: 承認必須変更

新機能・利用者体験の仕様変更、許可されるNode能力や権限範囲・隔離の保証水準の変更、利用者に影響するTSF/OS登録仕様、正式ABI/契約の破壊的変更、CIの安全ゲートの弱体化、ライセンス・公開設定・公式配布方針、運用ルールの改定など。**内部の隔離実装を触るだけではLevel 3にしない。**

**事前の仕様承認と、マージ時のメンテナー承認が必要。** AIによる自動マージは禁止する。独立レビューは一律必須とはせず、リスク・未検証事項・メンテナーの指示に応じて実施する。

### 文書のみの変更に対する検査・レビュー例外

**実行コード・ビルド設定・CI設定・テスト/fixture・配布成果物・依存関係・実行時動作に影響しない文書のみのPR**では、GitHub Actions CIの成功をマージの必須条件から除外できる。独立レビューは通常の変更でも原則任意とする。

- 対象は説明文、表記、既存仕様に基づくガイド、リンク、移行記録などの**非実行の文書変更**に限定する。ファイルの拡張子だけで自動判定しない。
- 文書中のコマンド・運用手順、権限・セキュリティ方針、契約、公開・マージ権限などの**実質的な変更**は、文書のみでも該当するLevelと承認条件を維持する。CIや独立レビューの省略はメンテナー承認の省略を意味しない。
- `.github/`、スクリプト、ビルド/依存設定、テスト期待値、機械可読な仕様・配布マニフェスト等は文書だけとみなさない。
- CIを省略する場合でも、変更差分・リンク・記述の整合性を確認し、「文書のみ・実行影響なし」「省略した検査」「Levelと承認根拠」をPRに記録する。
- 文書以外の変更が混在する場合は例外を適用しない。影響が不明なら通常条件を適用する。
- CIが実際には失敗・未実行であるとき、合格したとは記載しない。GitHub側で必須チェックが設定されている場合はそれを迂回しない。

### 全レベル共通のマージ条件

1. Issueの合意範囲または許可された自律作業の範囲を守る。
2. 変更に対応する必須の検査が最新の対象コミットで成功している。ただし上記の文書のみの例外を満たす場合はCIを省略可能。文書整合性の検査は省略しない。
3. 実装担当AIが最新の差分を自己点検し、仕様逸脱、回帰、不正な権限変更、テスト不足、不確実性をPRへ簡潔に記録する。独立レビューは原則任意とし、必要と判断された場合、またはメンテナーが要求した場合には完了するまでマージしない。
4. 互換性、正式fixture、安全性、権限・終了保証を無断で弱めない。
5. 競合・未解決依存・明示されたマージ禁止がない。
6. PRに差分、検査結果、自己点検の要約、未検証条件、必要に応じた独立レビュー結果が記録されている。
7. ブランチ保護・Required checksなどGitHub側の条件を満たす。

CIのジョブ未起動、請求上限、タイムアウト、スキップは**合格ではない**。ローカル検査はCI合格の代用ではない。自己点検を独立レビューと偽って記録しない。必要な独立レビューを要求済みで、まだ完了していない場合はマージしない。

### 追加の独立レビューを求める条件

独立レビューは固定的な別AI呼び出しではなく、次の状況などで追加する。

- 実装AIが正しさを説明できない、あるいは重大な不確実性が残る。
- CIだけでは重要な動作を確認できない。
- 既存仕様との整合性に複数の解釈がある。
- 隔離、権限、秘密情報、Worker終了などに重大な安全上の懸念があり、追加の独立確認が問題の解消に役立つ。
- メンテナーが独立レビューを指定した。

独立レビューを行う場合は、別セッションのCodex等でもよい。リポジトリ全体ではなく、原則PR差分・関連Issue・契約・必要な周辺実装に対象を絞る。Claudeや異なるモデルは必須としない。レビューによって重大な問題が明らかになった場合は解消するまでマージしない。

## 6. 品質・検証

| 変更 | 原則必要な検査 |
| --- | --- |
| 文書 | リンク、例、記述整合性、差分 |
| Rust | 担当テスト、`cargo test --locked`、fmt、clippy |
| Editor/bridge | CLIビルド、`editor/` のnpm test / build、関係するUI検査 |
| Wasm/Host/隔離 | 実Wasm、権限、取消、実際の終了・回収、Windowsの該当実行テスト |
| 性能 | 同一条件での変更前後計測と機能・安全性回帰 |
| 配布 | 実配布物、固定成分・来歴、起動・終了の確認 |

テスト期待値を実装に合わせて弱めてはならない。契約変更は独立して承認を得る。旧リポジトリでの成功結果を新mainの合格とみなさない。必要なテストを実行できない場合は、未検証として記録し、該当変更の自動マージを行わない。

## 7. セキュリティ特則

- 外部Wasmの隔離を弱めない。暗黙のNative復帰を導入しない。
- 許可の自動付与、スコープ拡大、秘密・入力履歴・診断データの無断保存・配送は禁止する。
- タイムアウト、取消受付、論理完了と**実際のWorker終了**を混同しない。
- 安全性を強化する修正や隔離・Worker・権限検査の内部実装変更は、**既存の保証を維持することをテストと根拠で確認できればLevel 2以下としてAIに委任できる**。許可される能力や利用者への安全保証を変える場合はLevel 3とする。
- 自律実装の名目で検査を削除・弱体化してはならない。

## 8. 外部参加と公開

当面は外部からのIssueによる提案・バグ報告・検証結果を中心に受け付ける。**外部PRは自動マージ対象外**とし、仕様・安全性・著作権・コード取込権限を個別に確認する。

プロジェクト全体にOSSライセンスを付与していないため、提出されたコードの権利を推測して取り込まない。外部PRのコードをCIで実行する際は、fork由来の信用できないコードを前提に、トークン・シークレット・書込権限・成果物を保護する。GitHubの設定が未確認なら安全と決めつけない。

リポジトリのPublic化、旧repoのArchive、配布物署名、サポート・ライセンス方針の変更はメンテナーの判断事項。

## 9. 本体と処理Node

- 本体: Node非依存Core、system、Host/Worker/broker、Windows境界、権限、Editor、TSF、配布・診断。
- Node側: 変換・辞書・候補評価などの処理Node、テスト、配布パッケージ。
- 共通API/契約の正本は本体とし、Node側SDKは固定snapshotとして受け取る。
- Node側で変更が必要なら、まず本体側でIssueと承認済み契約変更を行い、後続のNode側Issue/PRで反映する。
- Nodeパッケージは独立にバージョン管理する。

## 10. 中断・引継ぎ

中断時は担当Issue/PR、作業ブランチ、HEAD SHA、完了差分、検査と失敗、残作業、未解決依存をPRへ記録する。引継ぎ先は実コードとGitHubの状態を再確認する。

## 11. ルールの改定

本ルール、[CONTRIBUTING](../CONTRIBUTING.md)、[AGENTS](../AGENTS.md)、[CLAUDE](../CLAUDE.md)で定義される権限・承認・安全条件を変更するにはメンテナーの承認が必要。ルール改定PRはLevel 3として扱う。
