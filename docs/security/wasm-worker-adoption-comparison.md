軽量 Wasm では起動、DLL の検証・ロード、コンパイル、終了と回収が支配的だった。コンパイル成果の再利用はその一部を削り、事前起動は準備が間に合う条件で費用を入力前へ移す。保持は起動の繰り返しを省ける。効果の大小は各試験内で評価する。

## 暫定判定

- **事前準備のみ**。現時点では汎用の事前起動プールを保留する。20 ms・2枠の補充不足が実測で確認された。コンパイル成果の再利用は入力単位の物理終了を維持できる候補として切り離す。通常 Host の結果と初回・メモリ・キャッシュ寿命まで確認して採否を決める。
- **B2のみ**。製品採用は保留。分離保持は既定2枠で入力用の枠を残せず、同居保持はモジュール間の OS 隔離が変わる。分離保持を提案する場合は、別 Job と入力実行枠を同時に確保できる条件を示し、入力ごとの物理終了からセッション単位の終了へ変える点を承認事項に分ける。
- **併用**。個々の適用条件を確認した後に比較する。プールと保持を足すと物理枠・回収の競合が起き得るため、別々の分位値を足して効果を見積もらない。
- **どちらも棄却**。既存保証を満たす候補の通常 Host での利得が確認できなければ、この結論も残す。現状のデータだけでは選ばない。

## 採用前に必要な対照

1. 同じ通常 Host、同じ入力、同じパッケージ・権限・物理上限で、使い捨て JIT と入力単位の終了を維持した成果再利用を比較する。異なる実 Wasm の直列、並列・合流、辞書と副作用ありの経路を区別する。初回、定常、20/100 ms の入力置換、物理回収、CPU/RAMを同時に記録する。
2. 成果再利用は検証済み Wasm と固定 DLL・エンジン設定・実行上限の一致を確認する。製品採用には、生成専用の隔離プロセスから正常終了後に得た成果だけを受け入れ、改変・差し替え・設定違いでは通常 JIT に戻せる根拠が必要。外部パッケージが供給するネイティブ成果は対象外。
3. 準備枠は対象の入力・文脈・権限が変わったら配送前に再照合する。無効な準備を使わず、上限に達した場合や準備失敗時には通常経路を維持する。失効、取消、保護、文書変更、異常終了で旧結果が公開されず、元プロセスと I/O が終わるまで予約を維持できることを確認する。
4. 保持案の比較では、入力途中の取消・文脈変更や Worker 異常終了が複数の所有者へ波及した場合の収束を測る。現行保証との差は提案として記録する。製品統合は #89 の採用決定後に扱う。
