## 通常 Host の入口で行った検査用対照

Windows x64 で通常の External Host と AppContainer Worker のデバッグビルドを使用。#85 と同じ二つの Wasm ハッシュだけを試験用ビルドでコンパイル対象に加え、検証済みの各モジュール像に独立した一時キャッシュを持たせた。両方式で同一の Worker・DLL・パッケージ・権限・入力・既定2枠を使用し、Host は既存の `compiled-module-jit-baseline` feature で比較側を切り替えた。JIT→再利用→再利用→JIT の順。各条件ウォーム24件/方式で、合計288件が正答し、各入力後に物理枠と Worker がゼロに戻った。

| 直列2段 Aのみ | 172.97 / 253.48 / 770.88 ms | 119.87 / 129.75 / 135.02 ms |
| 直列2段 A+B | 175.15 / 213.23 / 280.12 ms | 123.30 / 143.86 / 160.59 ms |
| 直列4段 A+B | 362.03 / 397.97 / 457.35 ms | 227.07 / 241.04 / 367.91 ms |

ウォーム中央値では各構成で約30–37%短縮した。ウォーム後の診断では JIT 側で実行段数と一致する compile 区間があり、再利用側では観測されなかった。両方式とも入力ごとに使い捨て Worker を起動する。上表の P99 は各セルの最大値に相当し、再現性のある上限とはみなさない。各 Host の最初の2段セッションを開く準備は JIT 約1.55–1.60秒、再利用 約1.56–2.75秒。既存の審査やプロセス準備も含み、キャッシュ生成単独の時間ではない。

試験用差分は Windows pilot の証跡に収録し、製品差分から分離した。比較には [#90 のドライバー](https://github.com/pitapa79/DIY_IME/pull/90) の `12 2 mixed WASM_B` を使用する。デバッグビルドと権限なし fixture の結果であり、配布版の効果、CPU/RAM、20/100 ms置換、資源権限付き経路、並行コンパイルと文脈変更の安全性はこの表の範囲外。

資源経路についてコードと既存診断を確認した。通常の公式モジュール呼び出しは、ハッシュと fuel / メモリ条件が一致すれば再利用対象になる。既存の辞書試験の公式経路には compile 区間なしの診断がある一方、準備済み辞書の producer / consumer は `--build-resources-v1` / `--resource-ranges-v1` で Wasm 原本を渡し、`resource_import::instantiate` が `module_new` を呼ぶため、成果再利用を通らない。既存ネットワーク試験は通常の呼び出しと再開を使うが、試験設定は fuel が null であり、固定 fuel を要求する再利用条件を満たさない。既存ログはネットワーク成功と区間を示すが、再利用の検証ではない。辞書・ネットワークの再利用性能はここから主張できない。

小標本・単一マシンの順次試験で、mixed P95 は最大値。権限付き経路の比較、CPU/RAM、キャッシュ寿命や安全性の検証は引き続き必要。生 JSON とログを Windows pilot に収録した。

## 原本 JIT 事前準備の入力置換比較に残る実装

#86 の原本 JIT 補充検査（2枠、32入力×2試行）は全入力を待つ検査であり、latest-input-wins の件数ではない。20 ms では予定時刻までの準備成功が4/64、100 ms では64/64。制御したコンパイル直前取消から実終了と回収を待って代替を起動する単発・1枠試験は、到着から代替終了の P50 / P95 が94.59 / 103.70 ms（16件）、取消から回収が14.26 / 24.98 ms。これは自然な到着分布でも2枠でもなく、20/100 ms 連続入力の fallback 率や正答率を表さない。#86 のログ `issue86-generic-raw-refill.log` と `issue86-generic-raw-precompile-fallback.log` に条件と生測定がある。

2枠の latest-input-wins 対照を安全に作るには、#86 の `src/isolated_worker/runtime/compiled_module_probe/generic_fixture.rs` の固定 `index` / `step_by(lanes)` と、各 lane が予定入力を必ず待って送るループを置き換える必要がある。入力到着時計と一つの現在 revision を持つ試験スケジューラが、準備中・ready・実行中・取消中・終了確認済みの各 Worker の所有者と取消 token を追跡し、未準備または旧 revision を取り消す。終了未確認の Job は枠を占有し続け、`src/isolated_worker/pipe.rs` の `Outcome::Exited` と回収後にだけ同じ枠へ fallback または補充を許す。2枠合計の live 数を常時記録し、上限違反で失敗させる。

通常実装への接続を検討する場合、`crates/runtime/src/execution_control/ledger.rs` の `invalidate_input_collected` と `dispatch.rs` の物理枠予約、`worker.rs` の CompletionPermit、`src/isolated_worker/adapter/gate.rs` の `begin` / `publish`、`adapter/mod.rs` の `start_legacy` / `call_traced`、`pipe.rs` の `Running` / 終了確認にまたがる。事前準備は現在の入力呼出しより前に存在するため、予約と所有権の受渡し、revision・権限・保護変更時の拒否、取消中に slot を再利用しない処理が必要である。既存の raw JIT 補充 harness はこれらを提供せず、準備用 worker を別枠で足すだけでは2枠上限を守れない。

測定ドライバーは `scripts/host-input-scenarios.mjs` のように20/100 msの予定時刻、実発行遅延、各 revision の正答・current・superseded・失敗と物理終了を別々に記録し、最後の current 入力まで drain する。試験の待機・置換・破棄規則と readiness race を明示し、旧結果の非公開と全終了を確認する。現時点では原本 JIT 事前準備と入力時 JIT の latest-input-wins 比較は未実施であり、上記の補充・単発値をその効果として扱わない。

## 暫定判定

[単段の置換シミュレーション #91](https://github.com/pitapa79/DIY_IME/pull/91) では、実プロセスを使って物理上限2を守り、20 ms間隔で完了した入力は通常起動4/32、事前準備6/32だった。100 msでは31/32、32/32だった。各方式とも準備中でまだ入力を受け取っていない Worker は最新入力に割り当てた。準備ミスによる代替起動は観測されていない。この小標本では、20 ms間隔の主経路に事前準備を採用する根拠は得られなかった。通常 Host の複数段・権限付き経路での置換は引き続き別の検証となる。

- **事前準備のみ**。現時点では汎用の事前起動プールを保留する。20 ms・2枠の補充不足が実測で確認された。コンパイル成果の再利用は入力単位の物理終了を維持できる候補として切り離す。通常 Host の結果と初回・メモリ・キャッシュ寿命まで確認して採否を決める。
- **B2のみ**。製品採用は保留。分離保持は既定2枠で入力用の枠を残せず、同居保持はモジュール間の OS 隔離が変わる。分離保持を提案する場合は、別 Job と入力実行枠を同時に確保できる条件を示し、入力ごとの物理終了からセッション単位の終了へ変える点を承認事項に分ける。
- **併用**。個々の適用条件を確認した後に比較する。プールと保持を足すと物理枠・回収の競合が起き得るため、別々の分位値を足して効果を見積もらない。
- **どちらも棄却**。既存保証を満たす候補の通常 Host での利得が確認できなければ、この結論も残す。現状のデータだけでは選ばない。

## 採用前に必要な対照

現行実装は固定公式 Wasm のハッシュをコンパイル側で照合し、その専用プロセスの実終了後に返った成果を Host が保管する。実行側では成果のハッシュを照合してから Wasmtime の unsafe なデシリアライズを呼ぶ。成果のハッシュは保管後の変更を検知できるが、生成元が返したバイト列と元 Wasm の意味が一致することまでは検証できない。一般の Wasm にこの方式を拡張すると、入力や資源を持たないコンパイル専用プロセスから、入力や資源を扱う実行プロセスにネイティブ成果を持ち込む経路が増える。正常終了とハッシュ一致だけでは、この経路が既存の保証を保つ根拠にならない。

現状の汎用キャッシュはこの理由で採用保留とする。次の比較では、使い捨て実行プロセス内で元の Wasm をコンパイルする経路を維持し、入力や権限を渡す前に準備する候補を優先する。コンパイルの前倒しが有利な間隔と、枯渇時に通常経路へ戻る費用を区別する。

1. 同条件比較を配布相当ビルドと権限付き経路まで拡張する。異なる実 Wasm の直列、並列・合流、辞書と副作用ありの経路を区別する。初回、定常、20/100 ms の入力置換、物理回収、CPU/RAMを同時に記録する。
2. 成果再利用は検証済み Wasm と固定 DLL・エンジン設定・実行上限の一致を確認する。製品採用には、生成専用の隔離プロセスから正常終了後に得た成果だけを受け入れ、改変・差し替え・設定違いでは通常 JIT に戻せる根拠が必要。外部パッケージが供給するネイティブ成果は対象外。
3. 準備枠は対象の入力・文脈・権限が変わったら配送前に再照合する。無効な準備を使わず、上限に達した場合や準備失敗時には通常経路を維持する。失効、取消、保護、文書変更、異常終了で旧結果が公開されず、元プロセスと I/O が終わるまで予約を維持できることを確認する。
4. 保持案の比較では、入力途中の取消・文脈変更や Worker 異常終了が複数の所有者へ波及した場合の収束を測る。現行保証との差は提案として記録する。製品統合は #89 の採用決定後に扱う。
