# 保持Workerの寿命所有（実装途中）

Issue #72、親 #27。A/B2の採用と[固定公式経路の契約](official-retained-pipeline.md)に従う。開始mainは `fd792529ddeedd8879e97cc1372ce5f83282667c`、依存は本体PR #71。Worker側ループ、native寿命pin、入力ごとの有界driverを追加した段階。通常Hostの選択・固定公式構成の判定は未接続であり、製品の保持方式が完成したとは扱わない。

## 追加したWorker側

Native専用 `--retained-resources-v1` は既存のAppContainer検査の後だけ受理する。引数はruntime、最大呼出し回数、fuel、Wasm memory、およびmodule/path長の組。DLLは既存の固定SHAとC APIを検証し、一度ロードする。moduleは1〜4個、各32MiB・合計64MiB、最大4096呼出し、fuel最大5B・Wasm memory最大128MiBに制限する。公式の適格性や利用者の許可を、この引数やNode名だけで認定しない。

module/EngineはWorker内で保持する。入力ごとのStore/Instanceとread callback環境を新規に作り、結果frameを書き出す前に破棄する。コード所有者と一回の呼出しを分け、呼出し側のDropはStoreだけを削除する。コード所有者がmodule/Engineを最後に削除する。callbackはStore削除まで生かし、読取用の保持経路に成果emit能力は追加しない。

全moduleのコンパイル後、Workerは `DIYRDY01` + module数u32LEのreadinessを返す。各呼出しのnative headerは `DIYRET01` + sequence u64LE + module slot u32LE。sequenceは1から連続し、slotは起動時の固定module配列内だけを許す。Workerは同じheaderをackした後、既存 `DIYRNG01` の有界read/resultを一回実行する。次の呼出しは新しいnative headerで始める。呼出し予算の最後も即終了せず、親の公開と競合しないようEOFを待つ。追加headerでは実行しない。単発経路の双方EOF検査は維持する。

## 有界の入力driver

`RetainedClient` と `RetainedInput` は信頼側の実行thread用API。実ExecutionHostと寿命予約は同じ資源domainでなければならない。固定したstage順序は予約の正確なbinding indexに対応し、同じmodule slotでも別grantや設定・資源版で代替しない。全bindingは同じGate、session epoch、plan versionに属する。これだけで公式構成の適格性や入力先文書の識別を証明したとは扱わない。

同時の入力guardは一つ、通信待ち行列は一件。Client構築時に返信workspaceを予約し、ClientとIO所有者がその寿命を保持する。Coreの入力受付より前に予約することで、保持済み出力の回収判断からこの費用が見えるようにする。入力受付ではqueued jobだけを予約し、実際に配送するserialized inputの長さを各callの前に別途課金する。最大入力量を一括予約してCoreの待ち行列全体を塞がない。実IOがその入力bytesの予約を保持し、replyで次段を起こす前に親側の入力bufferと予約を返す。

入力全体の要求量と返信frame累積量、各frame長、呼出し回数を有限にする。累積要求量の上限と、同時に保有する入力bufferに対するHostのqueued-input上限は別に検査する。JSONデコード後のRustオブジェクトや利用側のコピーを含む正確なRSS上限を、このbyte会計だけで保証しない。利用側のPacket検証・保持予算とOS Jobの上限も必要。

idleは最大60秒、入力期限は最大30秒。入力ごとに寿命tokenとは別の取消tokenを要求し、5ms間隔のwatchdogがstage間も取消と期限を監視する。各scope期限も入力期限を短縮する。入力途中の取消、guard放棄、不正応答、Nodeエラー、通信破損、過大入力では元Workerの寿命を取消し、そのプロセスを次の入力へ再利用しない。残る呼出し予算で全stageを実行できない入力は、最初のstageより前に拒否する。

`finish` はすべてのstageが完了した入力だけを扱う。Gateの現在性確認、元プロセスの終了観測との順序付け、入力取消・期限の確認の下で公開closureを呼ぶ。呼出元はclosure内でNode出力/Packet検証と既存Core CompletionPermitによる最新文脈・入力revisionの採用を行う必要がある。driver自身はUIを更新せず、通常Hostへのその接続は未実装。終了を観測した元handleの閉鎖と公開は同じmutexで直列化する。公開後のWorker死亡によって既に返した値を変更しない。

通常Coreが前段の出力を受け取ってから次段を開始するため、`publish_stage` では直前に完了した段の現在のCompletionPermitを公開できる。未実行段や同じ段の重複公開を拒否する。空入力等でCoreが残る全段をSkippedにした場合は、Hostが実際のCore終端を検証してから `finish_unexecuted_suffix` に正確な残りbinding列を渡す。実行済みprefixの全段が公開済みでなければ拒否し、呼出し予算を架空に増減しない。この入口自体はCoreのSkippedを証明しない。guestが自己申告する省略には使わない。

公開closureはGate lockを保持するため、同じGateを取る `GuardedController::get_run` 等へ再入しない。Coreの状態確認は外側で行い、段の公開は既存のCompletionPermitへenqueueする。Skipped終端のclosureは確認済みの終了処理だけを行い、入力結果を直接UIへ送らない。通常Host coordinatorと実Coreの接続は後続で検査する。

## 実Windowsで確認した範囲

`RetainedReservation` は実ExecutionHostから物理1枠とsnapshot総量を予約し、最大16 bindingのgrant・保護世代・module slot・同一Arcの資源版を保持する。複製は同じ予約の所有を共有する。一つの予約から起動できるプロセスは一度だけ。`execute_retained` は同じ取消token、有限walltime（最大600秒）/grace（最大5秒）、資源scope期限を要求し、`Running` が独立したpinを所有する。終了未確認の所有者やDropも、元process handleの実終了とIO回収前にpinを返さない。呼出元はACL等の清掃終了まで外側のpinを保持する。

元handleの終了通知を観測した時点で、IO joinより先に予約を閉じる。閉じた予約は認可や再起動に再利用できない。`is_closed` は制御状態であり、OS終了receiptや予約返却の証拠ではない。清掃pinが残る間は終了後も資源を計上する。異なるgrant/epoch・slot・同じbytesの別Arcへの差替えは拒否して寿命tokenを取消す。入力ごとにRunKeyが更新されても、同じplan/grant/不変資源なら照合できる。

資源を読まないstageには明示的な `ResourceRangeSession::open_empty` を使う。実行grantは必要で、すべてのreadを拒否する。従来の `open` と構築用の非空要件は弱めない。

`adapter::retained_tests::real_retained_module_loop` は、実Workerを `execute_retained` のAppContainer/Jobと実終了receipt経路で起動する。一つのプロセスに2 moduleを置き、状態を持つ検査用Wasmと公開SDK consumerへ交互に20回呼び出す。globalとlinear memoryのcounterが毎回1であることと、固定8 bytesの範囲読取の一致を検査する。これは製品Nodeではない。同じ予約の複製による二重起動拒否、実終了後の閉鎖、清掃pinの課金継続も確認する。

論理応答後もExecutionHostのphysical_jobs=1、retained_bytes=8を維持し、追加の物理枠取得を拒否する。親がstdinを閉じ、元process handleの終了とIO回収を確認した後、ACL/profile/cache/元の資源版を回収してから予約を返す。native header/slot/順序/全切詰めとゼロ・無制限予算、資源なしscopeのread拒否、grant/token/資源版の差替えも単体検査する。

`adapter::retained_driver_tests` は同じ公開SDK consumerと検査用Wasmを実AppContainerで実行する。通常10入力/20stage、開始前・stage間・Wasm実行中の取消、期限、guard放棄、別scope/計画、不正JSON、trap、要求量/回数上限、idle、公開直前の保護を検査する。実行中取消と期限は、Wasmの実read callback到達を確認してからの事象である。先の正常値を得た後に同じWorkerでtrapする負例も含む。終了未確認を観測した場合は、各retryで同じPIDと予約の継続を検査する。ローカル実Windowsでは9回の終了未確認retryを実観測した（OSの終了速度次第で回数は変わる）。別ケースでは正常な最終応答後に寿命を取消し、元processの実終了receiptを受け取ってから `finish` を試み、公開closureが実行されないことを確認する。毎回の実終了receipt後にACL/profile/cacheを清掃し、最後に予約がゼロになることを確認する。これらの実Windows検査はSDK検査スクリプトからも実行する。合成検査HostからのAPI利用であり、通常ExecutionServiceやCoreの結果保管への接続の証明ではない。
