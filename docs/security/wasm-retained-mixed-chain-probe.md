# 異なる Wasm を含む四段グラフでの保持 Worker 試験

#87 / #84。開始点は main `bb5293ba2bbbcd2d34a764221aeb2afaa4128470`。Windows x64、[main CI 配布物](https://github.com/pitapa79/DIY_IME/actions/runs/42555426096/artifacts/13648045743)の実 Worker と Wasmtime を使用。検査用 Node は文字列をそのまま渡す。実コードの異なる二つの Wasm を A→B→A→B に接続した。両 Wasm は同じ検査用ソースから別の最適化レベルで生成し、コードセクションの SHA-256 が異なることを確認した。

同じ Core 計画、許可、Worker 制約、入出力、終端待ちで、使い捨て→保持→保持→使い捨ての順に各24件を実行した。どちらも48/48正答し、全四段の結果を入力文字列と照合した。保持方式では各試行内で PID が同じであり、実行した四段から入力ごとに四つの応答を確認した。全試行でセッションを終了し、所有資源の計数がゼロに戻り、試験用コード資産のディレクトリが片付いたことを確認した。

| 方式 | ウォーム46件 P50 / P95 / P99 | 最初の応答 | セッション終了後の回収 |
| --- | ---: | ---: | ---: |
| 段ごとに使い捨て | 341.41 / 353.86 / 381.45 ms | 345.32–345.93 ms | 1004.37–1015.64 ms |
| 四段を保持 | 2.80 / 2.92 / 3.01 ms | 3.50–3.84 ms | 1003.79–1009.47 ms |

保持の準備は111.90–119.51 ms。表は入力更新から終端結果と物理コールバック数ゼロの観測まで。準備、セッションの実終了・回収、通常 Host の許可審査と公開は区間外。入力更新後に旧結果が Core で現在の結果として扱われないことを確認した。保護を有効にすると旧 Controller からの照会が拒否され、保護解除後も旧 Controller は無効だった。回収値は Controller・Service の破棄、コード資産の解放、テスト用ディレクトリの片付けを含む。1回の入力の物理終了とは別の境界。試行の初期版では、使い捨て対照のテスト変数が使わないステージ参照を残し、片付けが期限切れになった。参照を明示解放して再測定した。

## 再現

同じ条件で、段数を変えた追加試験も実施した。各条件は8件正答。下表は初回を除く7件の中央値で、裾の分位点を判断するには少ない。保持側の初回準備は92–124 ms。全条件で入力の失効、保護後の照会拒否、所有資源とコード資産の回収を確認した。

| 直列段数 | 使い捨て P50 | 保持 P50 |
| ---: | ---: | ---: |
| 1 | 85.67 ms | 1.09 ms |
| 2 | 169.64 ms | 1.64 ms |
| 8 | 680.41 ms | 5.25 ms |
| 16 | 1387.88 ms | 10.81 ms |

4段以外では試験から内部の構築関数を直接呼ぶ。製品側の入口は従来どおり4段を要求する。

#85 の検査用ソースから標準 release と `CARGO_PROFILE_RELEASE_OPT_LEVEL=2` を異なる target ディレクトリでビルドする。標準と代替の絶対パスを `DIY_RETAINED_HOST_FIXTURE_WASM` と `DIY_RETAINED_ALT_FIXTURE_WASM` に設定する。配布物の Worker と DLL を `DIY_RANGE_WORKER_BINARY` と `DIY_RANGE_RUNTIME_DLL` に指定する。

```powershell
cargo test --locked --lib compare_core_mixed_chain -- --ignored --nocapture
cargo test --locked --lib compare_core_chain_lengths -- --ignored --nocapture
cargo test --locked --lib compare_core_chain_cadences -- --ignored --nocapture
```

4段に対して20 ms・100 ms間隔で各16件を予定し、前の入力の実行が終わってから次を受け付けた。全条件で16/16正答し、旧入力の失効、保護後の照会拒否と回収を確認した。

| 間隔・方式 | 受付から応答 P50 | 予定から受付 P50 | 予定から応答の最大 |
| --- | ---: | ---: | ---: |
| 20 ms・使い捨て | 343.98 ms | 2362.25 ms | 5297.75 ms |
| 20 ms・保持 | 3.28 ms | 0.25 ms | 4.05 ms |
| 100 ms・使い捨て | 339.88 ms | 1677.06 ms | 3963.03 ms |
| 100 ms・保持 | 3.20 ms | 0.16 ms | 4.10 ms |

これは処理が詰まったときの待ちを見えるようにする試験。通常 Host のように処理中の入力を即座に置換する負荷は別の測定となる。

試験は直接 Core の検査用構成に保持所有者を接続する。通常 Host の適格性判定は試験対象外。相互に異なる Wasm が同一 AppContainer を共有する場合、OS 分離の単位と結果の採用時点が従来と異なる。これらの仕様判断は #88 で扱う。分岐、権限付き資源、CPU/RAM、実行中の取消・異常終了は次の比較に残る。
