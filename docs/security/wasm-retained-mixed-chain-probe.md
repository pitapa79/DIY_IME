# 異なる Wasm を含む四段グラフでの保持 Worker 試験

#87 / #84。開始点は main `bb5293ba2bbbcd2d34a764221aeb2afaa4128470`。Windows x64、[main CI 配布物](https://github.com/pitapa79/DIY_IME/actions/runs/42555426096/artifacts/13648045743)の実 Worker と Wasmtime を使用。検査用 Node は文字列をそのまま渡す。実コードの異なる二つの Wasm を A→B→A→B に接続した。両 Wasm は同じ検査用ソースから別の最適化レベルで生成し、コードセクションの SHA-256 が異なることを確認した。

同じ Core 計画、許可、Worker 制約、入出力、終端待ちで、使い捨て→保持→保持→使い捨ての順に各24件を実行した。どちらも48/48正答し、全四段の結果を入力文字列と照合した。保持方式では各試行内で PID が同じであり、実行した四段から入力ごとに四つの応答を確認した。全試行でセッションを終了し、所有資源の計数がゼロに戻り、試験用コード資産のディレクトリが片付いたことを確認した。

| 方式 | ウォーム46件 P50 / P95 / P99 | 最初の応答 | セッション終了後の回収 |
| --- | ---: | ---: | ---: |
| 段ごとに使い捨て | 341.41 / 353.86 / 381.45 ms | 345.32–345.93 ms | 1004.37–1015.64 ms |
| 四段を保持 | 2.80 / 2.92 / 3.01 ms | 3.50–3.84 ms | 1003.79–1009.47 ms |

保持の準備は111.90–119.51 ms。表は入力更新から終端結果と物理コールバック数ゼロの観測まで。準備、セッションの実終了・回収、通常 Host の許可審査と公開は区間外。入力更新後に旧結果が Core で現在の結果として扱われないことを確認した。保護を有効にすると旧 Controller からの照会が拒否され、保護解除後も旧 Controller は無効だった。回収値は Controller・Service の破棄、コード資産の解放、テスト用ディレクトリの片付けを含む。1回の入力の物理終了とは別の境界。試行の初期版では、使い捨て対照のテスト変数が使わないステージ参照を残し、片付けが期限切れになった。参照を明示解放して再測定した。

## 異なる Wasm を別々の AppContainer に保持

同じ A→B の2段、同じ許可・入力・物理上限4で、使い捨て、同居保持、分離保持を交互順で各2試行した。各方式32/32正答。分離保持では各試行内で異なる二つの PID を確認し、入力ごとに各 Worker が一つずつ応答した。保護後に旧 Controller が結果を返さず、セッション終了時に所有資源と試験用コードが回収された。

| 方式 | ウォーム30件 P50 / P95 / P99 | 準備 | 常駐の物理枠 |
| --- | ---: | ---: | ---: |
| 使い捨て | 173.59 / 190.48 / 196.04 ms | 各入力の応答区間に含む | 0 |
| 同居保持 | 1.68 / 1.72 / 1.85 ms | 107.75–112.11 ms | 1 |
| 分離保持 | 1.63 / 1.77 / 1.80 ms | 109.64–115.91 ms | 2 |

分離保持は別の AppContainer/Job でモジュールを動かしながら、入力ごとの起動を省く。今回の差は小さく、両保持方式の速さを順位付けする根拠には使わない。比較時の物理上限は4で、配布版既定の2枠で使えることは実証していない。入力ごとに OS プロセスを終える保証は両保持案で変わるため、適用範囲と公開条件は #88 の比較・承認事項。通常 Host への変更を行う前に、入力更新や取消中の二つのプロセスの収束、分岐・権限付き資源、上限時の安全なフォールバックを確認する。

```powershell
cargo test --locked --lib compare_core_isolation_groups -- --ignored --nocapture
```

別の計測で各方式24件を20 ms間隔で予定し、入力処理区間の Worker のみを約16 ms間隔でサンプリングした。各方式2試行。保持方式の区間には準備を含まない。

| 方式 | 合計ワーキングセットのピーク | 合計プライベートメモリのピーク |
| --- | ---: | ---: |
| 使い捨て | 48.63–49.11 MiB | 50.23–50.94 MiB |
| 同居保持 | 25.11–25.89 MiB | 9.70–10.49 MiB |
| 分離保持 | 42.35–43.61 MiB | 16.48–20.20 MiB |

分離保持で観測した追加メモリは、同居保持に対してワーキングセットで約16–19 MiB、プライベートメモリで約6–11 MiB。合計ワーキングセットにはプロセス間の共有ページが重複する場合がある。使い捨ては予定より遅れて完了したため、保持方式とは計測区間の長さが異なる。保持中のプロセス CPU 増分は各試行 0–15.625 ms と計測粒度に近く、方式間の順位付けには使えない。使い捨ての短命プロセスでは終了直前の CPU 時間を取り切れない場合がある。生ログは Windows pilot の証跡 ZIP に収録する。

```powershell
cargo test --locked --lib profile_core_isolation_groups -- --ignored --nocapture
```

### 既定の物理上限2での枯渇と復帰

同じ2段で物理上限を2にすると、使い捨てと同居保持は各8/8正答。分離保持は準備できたが、二つの寿命予約で上限に達した。Core のコールバックは別の実行枠を必要とするため、入力は待ち行列に留まり、Worker への送信は発生しなかった。最初の試行では20秒の試験期限に達した。

回復試験では待ち行列に1件、実行中0件、保持枠2を確認した。入力を取り消すと実行枠の使用なしで終端に達し、二つの所有者を閉じると保持枠は0に戻った。その後、新規入力を通常経路で8/8正しく処理し、終了時の資源回収も確認した。この回復操作は試験ドライバーが明示的に行った。

採用を検討する際は、上限2では分離保持を開始せず通常経路へ送る案を優先する。上限が大きい構成でも、入力実行枠を残せることを競合のある状態で確認する必要がある。通常 Host の経路切替や枠の会計は変更していない。

```powershell
cargo test --locked --lib compare_core_isolation_groups_at_default_capacity -- --ignored --nocapture
```

## 異なる2モジュールの並列出力

通常 Core の検査用 graph を追加し、同じ input から異なる実 Wasm A/B へそれぞれ枝を伸ばし、独立した2つの出力を同時に targets とした。容量4枠で、使い捨て対照とモジュール別の2保持 owner を対照→保持→保持→対照の順に各16入力比較。計64実行・128出力を入力文字列と照合し、各実行が terminal かつ input 用物理実行・待機ゼロになったことを確認した。保持側は2つの異なる PID と2つの予約枠、各 owner の応答数を検査した。session close 後に owner を破棄し、Host の全資源使用量がゼロになり作業領域を回収できたことを確認した。

| 方式 | 各試行の初回 | 先頭除外30件 P50 / P95 / 最大 | owner の準備時間 |
| --- | ---: | ---: | ---: |
| 使い捨て | 109.90 / 103.95 ms | 107.71 / 158.57 / 651.13 ms | 0 owner |
| 2分離 owner | 1.75 / 1.74 ms | 1.24 / 1.31 / 1.32 ms | 107.66 / 105.31 ms |

これは単一マシンのデバッグ検査、合成 fixture と直接 Core の計測である。グラフは独立出力の並列分岐であり、合流処理を測っていない。2つの保持プロセスは各入力の正答時点では終了せず、session close での物理終了と回収を検査した。並列実行の時間的な重なり、通常 External Host、権限・保護変更中の並列動作、20 / 100 msの入力置換、同時メモリピークはこの測定では証明しない。生ログは `issue87-parallel-independent.log`。

```powershell
cargo test --locked --lib compare_core_parallel_independent_outputs -- --ignored --nocapture
```
## 分離 owner の片側異常終了

上の2分岐・異なる2モジュール・容量4枠で、stage1 の検査用 Wasm を入力中に停止する構成にした。2つの保持 owner の異なる PID を確認し、stage1 が入力を受理した後にその PID のプロセス handle を開いた。対象が未終了であることと owner の PID が一致することを確認して、その handle だけに `TerminateProcess` を実行し、OS の signal を待った。もう一方の owner は終了直後も未終了と確認した。

その入力の Core snapshot は current のまま terminal となり、配送は `Failed`、原因は stage1 の `retained-transport` だった（terminal reason は `Completed`）。完了時に入力用の running / cancel-requested / stalled / queued がゼロとなり、session close 後は両 owner の thread を join、Host 全資源がゼロとなって試験用作業領域も削除できた。1回の決定的な synthetic fault であり、通常 External Host の公開応答、実際の第三者 Node、他の同時入力や再起動後の成功、保護・権限変更との競合を証明しない。生ログは `issue87-split-owner-fault.log`。

```powershell
cargo test --locked --lib split_owner_termination_during_input -- --ignored --nocapture
```
