# 固定公式経路の辞書範囲取得と Worker 保持

状態は事前仕様承認済み、製品実装前。[Issue #53](https://github.com/pitapa79/DIY_IME/issues/53) の A と B2 を、2026-11-07 のメンテナー指示「両方採用」で採用した。契約タスクは [#59](https://github.com/pitapa79/DIY_IME/issues/59)、性能と統合の親は [#27](https://github.com/pitapa79/DIY_IME/issues/27)。開始 main は `fd792529ddeedd8879e97cc1372ce5f83282667c`。

この契約に従う実装を段階的に追加する。現行の guest API v1、通常の一回限りの Worker、既存 Graph と Packet の互換性は各段階で検査する。Level 3 の製品マージは別途メンテナー承認を要する。

## 適用範囲

初期対象は、Host が内容ハッシュと Node 定義を検証した固定公式のローマ字変換、完全一致辞書、候補選択、文字列化を使う経路。同じ承認済みの実行計画と入力先の文脈の中で Worker を保持する。任意の Node を名前だけでこの経路へ昇格させない。

実際のモジュール、設定、必要能力、資源方針を照合して選択する。第三者 Node やネットワーク・秘密・書込能力を含む構成は既存の実行方式を使う。固定公式構成を混ぜた任意グラフ全体へ、この契約を拡張しない。ユーザーが構成できる既存のグラフは引き続き利用できる。

Host は配線・認可・資源の所有・実行と公開を担当する。辞書の形式、索引構築、読みの照合、候補生成、順序と score は処理 Node が担当する。既存の [Node 契約](../node-contracts-v0.1.md) と [設計思想](../design-philosophy.md) に従う。

## 準備と辞書の固定

既存の [辞書 broker](wasm-dictionary-broker.md) の ResourceRoot、明示許可、相対参照、捕捉した不変バイト列を再利用する。

1. Host はコード・Node 定義と版・設定・資源方針・許可を照合し、承認済み参照から原本を捕捉する。レビューや未承認の段階では本文を読まない。
2. 隔離内の Node が原本の全件を検査し、実行用の索引と候補データを生成する。末尾の不正行、重複、文字コード、形式と既存上限の検査を含める。未読部分に不備があっても一部だけを成功として採用しない。
3. 生成物は Node 固有の不透明なデータとして Host が上限付きで回収する。構築 Worker の正常な実終了、IO 回収、許可と取消の再確認を経て準備完了とする。生成物を Host の辞書オブジェクトや Wasmtime のコンパイル済みコードへ復元しない。
4. 原本の版、生成コードのハッシュ、Node 定義・設定、成果形式の版と成果バイト列を結び付ける。消費側 Node でも形式・範囲・読みと候補の整合性を確認する。成果のハッシュ一致だけで原本との意味の同一性を保証しない。
5. 全準備が成功し、現在の許可を保つ場合だけ計画を原子的に切り替える。失敗時は既存の稼働計画と辞書を維持する。

Host は実行中の版を所有し続ける。原本の変更・削除や別名での再解決で、稼働中の辞書を変更しない。再準備は新しい捕捉と全件検証を行う。旧版を使用する Worker の実終了まで、その版の所有を保つ。

原本、構築中・稼働中・旧版の成果、構築 Worker、同時準備の件数とメモリを別に計上し、Host 方針の上限内で管理する。検証済みコンパイル成果と、辞書の非信頼な準備成果は所有と検証経路を分ける。

## 範囲の取得

Host が発行した不透明な資源 ID に対して、隔離内の Node が必要なバイト範囲を要求する。Worker の native 側が現在の要求に結び付けて broker へ転送する。Node は辞書の検索を実行し、Host はバイト列の範囲と認可を検査する。

| 要素 | 契約 |
| --- | --- |
| 資源 ID | 現在の計画と Worker に結び付く Host 発行 ID。同じ数値の再提示だけで別資源へアクセスできない |
| offset と length | 非負の offset と正の length。加算のオーバーフローと資源終端の超過を拒否する |
| 返答 | 承認済みの同一版から要求した長さの bytes を返す。短い読取や失効を成功・未知語へ変換しない |
| 読取方針 | 一回の最大バイト、入力ごとの回数・累積バイト、同時要求、実行期限を有限にする。上限値は Host が固定する |
| 検査時点 | 要求受付、配送直前、結果公開直前に現在性と取消・許可・保護を確認する |
| 課金 | 配送前に予算を予約する。同じ要求の重複や失敗・再試行で予算を回避できない |
| 権限 | 許可された資源のページを読める能力。特定の読みの検索だけができる保証とは区別する |

接続自体を Host の Worker 所有者に結び付ける。資源 ID、要求 ID、世代を Node が自己申告しても権限にはならない。メッセージの ID と現在の要求の対応、順序、重複、最大フレーム長を native 境界で検査する。ネイティブパスや許可トークンを Node へ渡さない。

Node が使う範囲取得インターフェースと成果 import/export は、後続の実装タスクで guest v1 と共存できる版付きの契約へ具体化する。現行 v1 の入力へ未対応のフィールドを黙って追加せず、Host と対応 Node の両方が検証した場合に新経路を選択する。

衝突する索引キーでも元の読みを完全照合する。候補が複数ページに分かれる場合は必要な全ページを取得・検査してから結果を公開する。上限超過や途中失効で、候補を切り捨てた部分結果を成功にしない。

## Host 側の範囲読取 API

段階2の基盤として、`adapter::ResourceRangeSession` が既存の `ExecutionGate` と実行 lease を使って、不変の `Arc<[u8]>` を所有する。Host が完全な準備検証を終えた当該設定の資源だけを `open` に渡す。`open` 自身は辞書や生成成果の意味を検証しない。

`ResourceRangeLimits` は資源件数・保有総量・単一/累積読取量・回数・期限を固定する。`descriptions` の ID は接続内だけで有効。`ResourceRangeRequest` の要求番号は1から連続して受理し、`read` は現在のleaseの下で予算を確保して、要求範囲を所有バッファへコピーする。範囲外・予算超過・重複・失効の後はそのセッションを閉じ、同じ実行の取消tokenを設定する。

これらは信頼側Rust APIで、guest向けのwire型や許可トークンではない。返ったbytesはメモリ内で承認された応答で、Worker/Nodeへの配送と公開は後続のnative transportの現在性確認に従う。配送所有者は実終了まで元プロセスとIO・資産を保持する。通常Hostとの接続、準備成果の生成、Nodeの範囲取得インターフェース、保持Workerの会計は後続で接続する。

## Worker と入力ごとの実行

Worker は一つの Host 所有者、承認済み計画、入力先文脈と辞書版に所属する。実行コード、設定、許可、保護、入力先文脈の境界を越えて再利用しない。

同時に実行する入力は一つ。Host が現在の入力を受け付け、各段で新しい Store/Instance と入出力を作り、段の完了後に破棄する。DLL、Engine、検証済み Module は Worker の寿命内で再利用できる。Node に前の入力や Store を渡さない。Store の破棄と OS プロセスの終了は別の事象として扱う。

未完了の入力を取消・置換する場合、まずその入力を失効させて公開と追加配送を止める。初期実装ではその Worker を停止し、実終了と回収を確認してから後続用 Worker を用意する。取消後のプロセスを次の入力へ引き渡さない。正常に完了した入力の間は Worker を保持する。

通常 Host の既存 context 世代、SessionEpoch、planVersion、input revision と配送世代を用いて現在性を照合する。文脈の切替を識別できる Host の接続範囲に限定し、TSF の実 Document/Context/Selection への適用は [#49](https://github.com/pitapa79/DIY_IME/issues/49) の別工程で扱う。

## 結果の採用と後発の失敗

B2 では、固定公式経路の有効な応答を入力ごとの正常実終了より前に採用できる。既存の一回限りの Worker では [ExitReceipt](worker-pipe-ownership.md) を要求する経路を維持する。

採用時には、上限付きのフレーム・厳密な JSON と Packet・Node の出力契約・要求 ID と実行順・現在の入力先文脈・最新 revision・許可と保護の世代を検査する。状態の確認と結果の公開を、同じ Host の順序付けの下で行う。現在性確認と公開の間に失効した結果を採用しない。

後発の Worker 異常終了によって、既に採用した有効な応答を取り消したり、過去の成功を失敗へ書き換えたりしない。未採用・実行中の要求は失敗させ、その Worker を廃棄する。新しい実行は再度コード、許可、計画と資源の現在性を検査する。失効済みの計画を自動で復活させない。

ここで採用する応答は、Host の構造・契約検証を通った応答を指す。任意 Node の内容の意味や、未来の正常終了まで証明する仕組みとは扱わない。[#52](https://github.com/pitapa79/DIY_IME/issues/52) が実証した保証差を、今回の採用範囲として記録する。

## 物理所有と回収

入力の論理完了と、保持 Worker の物理的な寿命を分ける。保持中も process handle、Job、AppContainer profile、IO、コード・辞書版の所有と物理的な資源枠を Host が保持する。

既存の CompletionPermit の完了や成功出力の配送だけで、保持プロセスの物理枠を解放しない。専用の寿命所有者と入力ごとの論理完了を結び付け、実行管理と資源計数へ接続する。新しい入力の受付も、所有者と残予算を確認する。

取消、期限切れ、権限撤回、保護開始・解除、文脈切替、計画切替、Session/Host の close、通信破損、コード資産の異常では新規配送・公開を止める。停止要求や EOF を実終了 receipt として扱わない。元の process handle の終了通知、IO の回収と資産 lease の清掃を追跡する。終了未確認なら同じ所有者が保持を継続し、代替プロセスの終了で完了にしない。

再起動中と旧 Worker の終了待ちにも上限を適用する。入力の速さを理由に、生きたプロセスや辞書版を計数から外さない。既に渡した入力・資源 bytes の消去を、停止 ACK や Store 破棄だけで保証しない。

## 実装と検査の順序

| 段階 | 実装する範囲 | 完成の証拠 |
| --- | --- | --- |
| 1 | 版付きの準備成果と資源範囲の Host/Node 境界 | 対応 Node を識別し、全件検証・構造・形式版・上限・改変・原子的切替・旧版所有を検査 |
| 2 | Host が所有する有界の範囲配送 | 別資源・別計画・別許可の拒否、offset/length の境界、予算、重複、途中失効と回収の検査 |
| 3 | 固定経路の保持 Worker と入力ごとの Store/Instance | 複数入力の正答と状態残留、応答前後の異常、取消、再起動、実終了・IO回収、物理資源計数の検査 |
| 4 | Node リポジトリの対応と通常 Host の接続 | 固定 SDK と公式成果を別 PR で更新し、既存 v1/第三者経路の回帰と新経路の選択条件を検査 |
| 5 | 実用辞書と通常 Host の同条件計測 | 実 Windows/実配布版、十分な分母、正答・旧応答抑止、入力/候補/確定/Backspace/取消/保護/文脈切替を確認 |

段階1の成果形式と Node 対応は Node リポジトリで行う。Host はその不透明データの所有と承認を担当する。各段階を対応 Issue と PR に分け、後続が未接続の段階を製品の完成と呼ばない。

性能の基準には、実用辞書、通常の入力列、候補の意味と正答、グラフ、配布物、測定の始終点、Windows と対象入力先を固定する。合成100万件の索引に日本語キーが少数ある試験だけで、実用辞書の合格にしない。

逐次と20/100ms、cold と warm、準備・再補充、予定と受付からの遅延、P50/P95/P99と最大、成功・失敗・置換の分母、親と Worker の CPU/RAM、物理終了と回収を記録する。採用した方式でも通常 Host の測定で P95 10ms・P99 20ms を達成するまで #27 を完了にしない。

## 今回の性能優先順位

通常の候補規模で、かな・漢字候補・確定を使える状態までの性能を先に検証する。4,096文字級の表記が多数ある大候補群の性能最適化は後続へ分ける。この優先順位を、既存の有効な候補の切り捨てや辞書全件検証の省略には使わない。

[#57](https://github.com/pitapa79/DIY_IME/issues/57) は固定合成経路の1,800件を正答し、保持方式の速度の見込みを示した。[#58](https://github.com/pitapa79/DIY_IME/issues/58) は大候補で本文の配送と全候補返信を含めると ID 化だけで目標に届かないことを示した。両者の測定範囲と入力条件を保って、通常 Host の比較へ引き継ぐ。

辞書の取得・同梱、外部データのライセンス、利用者向けの候補一覧の省略・遅延表示、汎用の候補 ID 型は別の採用判断になる。TSF の実装・登録・実アプリ測定は Windows 工程と #49 に従う。
