# Wasm実行基盤の安全性クラス別保証・性能仕様 v1.0

状態: **仕様 v1.0・Level 3**。承認・発効・移行の実施記録は [Issue #106](https://github.com/pitapa79/DIY_IME/issues/106) で管理する。2026-11-16、開始main `336442b4cb63c8411b67c90736e38af5f6599395`。

本書は、#106で指定されたS0/S1/S2と性能評価の正本候補である。**メンテナーが仕様PRのマージを承認し、mainへマージした時点で、この範囲の仕様として発効する。** 発効前は現行契約と#95を変更しない。発効しても、S1の製品採用・既定有効化や実装PRのマージを承認したことにはならない。

権限・変更レベル・検査・マージ条件の正本は[開発ガバナンス v1.2](../development-governance.md)。本書はAIの権限、CI安全ゲート、公開API、Nodeの能力を拡張しない。移行手順と旧要件の対応は[Goal移行案](issue95-goal-migration-v1.md)に示す。

## 1. 適用範囲と既存契約

通常Windows Hostが外部Wasm処理Nodeを実行する際の、単回使用・保持・同居の保証差と性能評価を扱う。[設計思想](../design-philosophy.md)に従い、ユーザーのグラフの自由や重いNodeの利用を速度で禁止しない。処理の意味はNode側に置き、Coreへ変換処理を固定しない。

[ノード分類](../node-classification.md)の「primitive」「標準機能」、作者、配布場所は安全性クラスと別軸である。分類名、公式という表示、署名やハッシュの自己申告だけで保持資格や能力を与えない。

既存の[固定公式経路の契約](official-retained-pipeline.md)、[静的照合](official-static-pipeline.md)、[通常Host接続](retained-host-integration.md)には、限定された構成への別途の承認・実装がある。本書はその廃止・拡張・再分類による一般採用を行わない。特に、既存の固定公式同居を根拠に、任意グラフのS2を製品採用済みと説明しない。その独立契約と回帰検査を維持する。

ここでのS0は汎用・未審査Nodeの基準経路であり、現在の全グラフがS0だけを使うという記述ではない。Graph/Packet/guest API v1、固定SDK、権限・設定・既定経路はこの仕様PRでは変更しない。

## 2. 実行モードと保証差

| 項目 | S0 | S1 | S2 |
| --- | --- | --- | --- |
| 位置づけ | 安全性重視の基準、未審査Nodeの標準経路 | 審査済みNodeの将来の標準候補。当面default OFF | 研究・実験専用。汎用方式として製品対象外 |
| Worker | 入力の当該Node実行ごとに隔離Workerを単回使用 | **Node別**AppContainer Workerを有限の寿命内で保持 | 複数の審査済みNodeがAppContainerを共有 |
| Wasm実行状態 | 当該実行専用Store/Instance | 入力・Node呼出しごとに新しいStore/Instance | 入力・Node呼出しごとに新しいStore/Instance |
| 正常入力の完了 | 元Workerの実終了と必要な回収を確認して結果を公開 | 正常入力ごとのプロセス終了は保証しない | S1と同じ |
| 過去入力のプロセス内残存 | 入力を受けたプロセスの実終了・必要な回収を確認 | Store破棄後もプロセスの割当領域等に残り得る。完全消去は保証しない | S1と同じ。共有故障領域のリスクも評価 |
| Node間のOS隔離 | 維持 | 維持 | 同居Node間には保証しない |
| 故障領域 | 実行を所有するWorker | 原則当該NodeのWorker | 同居する他Nodeにも停止・回復の影響が及ぶ |

S0のプロセス終了も、OSのページファイル、dump、ディスク、ブラウザー保存等を含む全媒体の完全消去を新たに保証するものではない。[入力保存の既存保証範囲](input-storage.md)と区別する。

S0では、入力をまだ受けていないWorkerの事前準備、検証済み不変コードのキャッシュ等を利用できる。ただし、入力を受けたWorkerの単回使用、元プロセスの実終了、IO/Job/ACL/profile/資産の必要な回収、公開前の現在性検証を維持すること。入力・結果・Store/Instanceの再利用をコンパイルキャッシュと呼ばない。

S1/S2が緩和するのは上表の明示した保証だけである。正常なStore破棄や論理完了を、プロセスの終了・入力消去・資源返却の証拠にしない。保護・権限失効・取消等で必要な物理終了を免除しない。

## 3. 全モードで維持する保証

1. 明示許可を越えるファイル、ネットワーク、秘密、OS能力へのアクセスを認めない。能力・設定・資源スコープと許可の失効を検証する。
2. Session、文書・入力先文脈、計画、入力revision、配送世代、対象Nodeを照合し、別文書や古い入力の結果を公開しない。識別子の一致を認可と同一視しない。
3. 保護入力を許可されないNodeへ渡さない。保護境界を越えて残せないWorker、IO、資源は停止・回収する。保護解除だけで旧入力や旧資格を復活させない。
4. Wasm境界、fuel、メモリ、実行時間、出力、同時Worker・待機・再生成中の有限上限を維持する。保持寿命や共有を使って予算を回避しない。
5. 元Workerのprocess handle、IO、Job、ACL、profile、コード・資源版、予約を終了まで追跡する。停止要求、EOF、完了通知、別PIDの終了を元所有者の終了証明にしない。実回収前に枠を不正再利用しない。
6. 取消・置換で旧入力の追加配送と結果公開を止める。寿命終了、保護、失効、取消・異常終了で必要な物理終了保証を残す。回復や再審査の間も旧所有者を会計から消さない。
7. Graph/Packet/Nodeの既存契約、正答、結果境界、現在のS0経路を維持する。guestの成功自己申告をHostの検証や意味的な正答の証明にしない。
8. 高速経路の失敗時も認可・保護を黙って緩めない。安全なS0への移行条件を満たさない場合は拒否する。

保持によってCoreを外部処理Nodeと同じプロセスへ移さない。S2の同居にも、Wasm境界や共有プロセスのAppContainer、資源上限は必要である。同居Node間にOS境界があるとは説明しない。

## 4. HostによるS1資格と失効

S1を選択する前に、Hostが実際に所有・検証した次の情報を審査記録へ結び付ける。

| 審査対象 | 必要な照合 |
| --- | --- |
| コード | 捕捉した実モジュールの完全な内容ハッシュ、版、Node定義と実装の対応、ランタイム・実行方針との適合 |
| 能力 | 宣言と実際のHost提供能力、明示許可、辞書・通信・秘密等の資源スコープ。能力なしだけで無条件に適格としない |
| 設定・依存 | 実際に検証した設定snapshot、依存コード、辞書等の捕捉版と保持期間。名前だけの参照や可変な再解決で差し替えない |
| 保持リスク | 過去入力の残存、状態・資源の寿命、取消・保護時の停止、故障からの復旧、有限な資源予約と最終回収 |
| 審査結果 | 対象コード・設定・能力・依存・実行文脈に限定した資格、根拠、再審査が必要な変更条件 |

作者が公式でも第三者でも同じ照合原則を適用する。「安全」「primitive」フラグ、Node名、外部から渡されたハッシュ、既存の実験用allowlistを、一般の審査制度が完成した証拠にしない。審査の保存形式や公開APIは本書では追加しない。

コード・版・定義・設定・依存・資源方針・権限・文脈の変更時には、影響する資格を再評価する。不明・失効・不適合な資格で新しい入力を配送しない。旧資格へrollbackして能力を復活させない。

S0へ戻す場合も、旧入力・旧Workerの停止と必要な回収、新しい実装・設定と許可・保護・入力世代の検証、予約、二重実行や副作用の回避が成立する場合に限る。失敗した呼出しを自動的に再実行する許可ではない。成立を確認できなければ、該当操作を明示的に拒否する。

S2の審査は、同居メンバー、相互の入力残存・能力・資源へのリスク、共有停止・回復範囲も対象とする。S1資格を持つことだけで同居資格を与えない。研究を行ってもS2の一般製品採用は認めない。

## 5. 性能目標の区別

| 対象 | 本仕様発効後の扱い |
| --- | --- |
| S0のNode Execution Overhead | 旧#95のP95 < 10ms / P99 < 20msを必達条件から外す。代替の固定必達値は当面置かず、測定・改善・制約の記録を続ける |
| S1の軽量Node Execution Overhead | **ノード実行ごとの基盤追加遅延P95 < 10ms / P99 < 20msを技術目標として維持**。実測の到達・未達と適用条件を示す |
| S2 | 固定必達値を設けず、S1との性能・資源・保証差を研究として記録 |
| Core Overhead | 既存の **P95 < 1ms** の目標を維持 |
| Reference IME Latency | [性能目標](../performance-goals.md)の実用構成全体の指標。Node単体の基盤追加遅延と別物であり、本仕様はその暫定目標や#27の完了条件を撤回しない |

基盤追加遅延は、受付・配送、実行管理、必要な隔離/ランタイム準備、Store/Instance作成、変換・IPC、認可/現在性確認、返信検証・公開、公開前に必要な終了・回収を含む。Node固有の変換・検索・推論・外部API待ちと、同一試行内で対応付けて区別する。「guest内時間」を一括で固有処理扱いにしない。

別試験のP95同士の減算、包含する工程の重複加算、異なるランナーのpercentileの合算をしない。測定区間やトレースが欠ける場合は欠落・上限/下限・guest込み等を明示し、基盤追加遅延の達成判定にすり替えない。20段の総応答時間を20で割ってノードごとのP95としない。

## 6. 測定と証拠

実Windowsの**通常Host**を使用し、選択された実行方式と資格、実プロセス・物理枠を確認する。診断専用経路、PoC、実験flagでしか有効でない方式の結果はその条件を明示し、既定経路やmainへの採用済みと説明しない。

| 軸 | 区別して評価する条件 |
| --- | --- |
| 構成 | 単段、直列2/4/8/16/**20**、並列、分岐・合流、登録済みだが未実行のNode |
| コード | 同一Wasmの複数利用、実行コードが異なるWasm、公式・第三者相当の混在。カスタムセクションだけ違うコード識別子は実コード差と区別 |
| 入力 | 初回/cold、warm、逐次、100ms/20ms連続入力、入力置換、空・Unicode・上限、出力上限/失敗 |
| 変更 | グラフ・設定・辞書・Session・文書・入力先、権限と資格の再評価 |
| ライフサイクル | 保護、失効、取消、通信破損、異常終了、Worker補充・再生成、長時間運用、完全な最終回収 |

未対応条件は理由と適用制限を報告し、成功件数から黙って除かない。対応するS0や既存固定公式経路の回帰を検査する。

記録には、コミット/実バイナリ・Wasm/ランタイムのハッシュ、Windows/CPU/メモリ、枠・寿命・入力上限、グラフ/設定/合成入力、測定始終点、試行数、P50/P95/P99/最大値を含める。正答・失効・拒否・busy・失敗・未分類の分母を分け、欠測をゼロにしない。失敗した試行のログ・部分結果と、採用/棄却/要修正の根拠を残す。

CPU/RAM/プロセス数、待機・旧版・再生成中の物理枠、入力callbackの終了と保持寿命の終了、元Worker/IO/Job/ACL/profile/資産の最終回収を区別する。Jobのcommit量や共有ページを重複計数するworking-set合計を、そのまま固有の物理RAM使用量と呼ばない。

同一条件の比較は同じ実バイナリ内で順序を釣り合わせる。異なるハードウェア/ランナーは別集計にする。少数試行のP99を一般保証にせず、試行数・分布・欠落トレースを明示する。実入力本文・秘密の無断保存を増やさず、証拠用の入力は既定で合成データとする。

## 7. 最新入力の復旧と判定

20ms入力では途中入力が後続により失効することを許容する。全途中入力が完了することは要求しないが、古い結果の公開、最新入力の消失、誤文書への公開は認めない。busyをguestの実行失敗と混同せず、最新入力が拒否されたまま消える場合を成功にしない。

最終入力について、信頼入力層での受領から現在の正しい結果の公開までを測る。試験では観測可能な入力発行点とHost受付点を明記し、入力予定からのスケジュール遅れも分離して報告する。内部retryやWorker再生成で開始時刻をリセットしない。正答に至らない最新入力の件数と理由も残す。応答後の物理終了・回収は別に記録する。

単段・4段・20段それぞれの、連続入力後の許容復旧時間と製品採用前の条件は**別途メンテナー判断**とする。[移行案の数値提案](issue95-goal-migration-v1.md#5-s1製品採用に向けた未承認の数値提案)は合格基準として未承認である。数百ms〜秒の復旧問題を、ウォーム単段の速さやCI成功で隠さない。

技術的な実装・計測・改善案の選択は既存ガバナンスに従って進める。製品採用の数値が未承認であることを、独立した安全検査や技術改善を止める理由にはしない。ただし、その未承認値でGoal Bや製品を合格扱いしない。

## 8. 完了と承認の境界

発効後は、#95を[移行案](issue95-goal-migration-v1.md)に従って **Goal A: S0改善** と **Goal B: S1技術的実用化** に分け、独立に報告する。S2は研究タスクへ分離し、#95完了の必須条件にしない。

- Goal Aは保証を維持した基準測定・改善・採否記録・通常Hostでの検証と引継ぎで判定する。10ms/20ms未達だけを理由に未完了にしない。
- Goal Bは資格、Node別隔離、新Store/Instance、寿命/会計、広い条件の正答・安全・復旧・最終回収を実証し、技術目標の達成/未達と実用応答の問題を明示する。重大な未解決の安全性・応答問題があれば要修正として完了にしない。
- 一方式の実装、子PR、単段PoC、CI一部または全件成功だけではGoal完了でない。技術的判定とS1の製品採用を分ける。
- 仕様・安全保証、S1既定有効化、S2製品化、未審査Node優遇、公開API/権限、検証条件の緩和はLevel 3として扱う。本書でS2製品化を承認しない。事前仕様承認と該当PRマージ時のメンテナー承認を省略しない。

実行方式や安全性の実証が困難な場合は、実測、失敗・代替案、保証差、影響、推奨をまとめて技術的な要修正/ブロッカーとして報告する。自動Goalの状態変更は、その実行環境とユーザーの停止・再開指示に従い、本書から新しい状態操作の権限を作らない。
