# 同じ隔離プロセス内でStoreを作り直す試験

[Issue #30](https://github.com/pitapa79/DIY_IME/issues/30)、開始main `5e2282f61d75decb100b77c0cb86d2faa89c2f35`。固定公式WasmとDLLは[公開Windows CI 42155771450](https://github.com/pitapa79/DIY_IME/actions/runs/42155771450) のartifact `13474977409`。Windows x64、Rust 1.90.0 GNUの開発用probeを使用しました。

```powershell
$env:DIY_COMPILED_PROBE_BUNDLE = 'C:\path\to\windows-app'
cargo test --locked --lib isolated_worker::runtime::compiled_module_probe::persistent -- --ignored --exact --nocapture
```

親が所有するコンパイル専用AppContainerの出力を検証し、別の実AppContainer/Jobで固定DLL・Engine・Moduleを保持しました。公式Nodeに合成の `kanji`、`kya`、`ky` を渡し、毎回Store/Instanceを生成・破棄します。計測区間は子の同じ時計で、Store生成、インスタンス化、ゲスト実行と応答の回収、Store破棄までです。正答照合は区間の直後です。

| 子の入力系列 | 正答／全件 | P50（ms） | P95（ms） | P99（ms） |
| --- | ---: | ---: | ---: | ---: |
| 待ちなし | 2,000 / 2,000 | 0.314 | 0.712 | 1.103 |
| 20 ms | 50 / 50 | 1.243 | 2.481 | 2.820 |
| 100 ms | 50 / 50 | 1.067 | 4.697 | 5.539 |

子内の予定に対する最大投入遅れは20 ms系列で8.673 ms、100 ms系列で8.432 msでした。表の分位点は投入遅れを含みません。最初のModuleロードと未使用Storeの破棄まで19.651 msで、DLLのロード・隔離プロセス起動を含みません。Jobの全2,100入力の累積CPUは875 ms、ピークコミット29.0 MB。最後に元のプロセスの実終了とパイプ回収を確認しました。

別の合成Wasmで線形メモリーと可変グローバルを書き換え、同じStoreで値が残る正の対照とtrapを確認しました。新規Storeで両方が初期状態に戻ることを64回照合しました。これはゲスト状態の検査です。プロセス内部のWasmtimeやOS資源、権限、秘密、古い継続に対する保証には別の検査が必要です。

## 親からのパイプ往復と途中廃棄

同じ配布物で `cargo test --locked --lib isolated_worker::runtime::compiled_module_probe::persistent_ipc -- --ignored --exact --nocapture` を実行しました。試験親は準備通知後に合成ケース番号を1件ずつ送り、完全な応答の受信・正答照合までを同じ親時計で計測します。子は応答前にStoreを破棄します。先行応答を待つ直列試験で、予定時刻からの投入遅れは別集計です。

| 親の入力系列 | 正答／全件 | P50（ms） | P95（ms） | P99（ms） | 最大投入遅れ（ms） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 待ちなし | 2,000 / 2,000 | 0.927 | 1.612 | 2.585 | — |
| 20 ms | 50 / 50 | 1.051 | 3.234 | 3.926 | 9.884 |
| 100 ms | 50 / 50 | 1.072 | 2.979 | 10.832 | 79.659 |

通常セッションのJob CPUは1,734 ms、ピークコミット29.0 MB。各50件のP99は最大値です。往復の値に準備時間と投入遅れは含めません。別の固定試行で、最初の正答の後に取消して元プロセスの実終了を確認しました。また、子を意図的に異常終了させ、ゲスト結果のフレームが返らず、実終了後に新しいプロセスで正答することを確認しました。

## 公式4 Nodeと合成辞書

`cargo test --locked --lib isolated_worker::runtime::compiled_module_probe::persistent_graph -- --ignored --exact --nocapture` で、同梱グラフと同じ4種類の公式Nodeを固定順に呼びました。各Nodeの呼出しごとにStore/Instanceを再生成し、前段のパケットを次段へ渡します。辞書は同梱3行、または同じ候補を維持して別読みを加えた合成1,000行です。両方で事前の辞書準備と、全入力の最終出力を照合しました。

未最適化ビルドの実パイプ往復は次のとおりです。投入予定の遅れは別集計です。

| 辞書行数 | 入力系列 | 正答／全件 | P50（ms） | P95（ms） | P99（ms） |
| --- | --- | ---: | ---: | ---: | ---: |
| 3 | 待ちなし | 200 / 200 | 1.571 | 3.181 | 3.736 |
| 3 | 20 ms | 50 / 50 | 2.094 | 3.198 | 5.114 |
| 3 | 100 ms | 50 / 50 | 1.832 | 2.874 | 3.066 |
| 1,000 | 待ちなし | 200 / 200 | 15.665 | 21.104 | 26.503 |
| 1,000 | 20 ms | 50 / 50 | 13.873 | 15.312 | 17.425 |
| 1,000 | 100 ms | 50 / 50 | 14.597 | 20.845 | 22.003 |

各セッションのJob CPUは3行547 ms、1,000行3,359 ms、ピークコミットはどちらも約29 MBでした。これは固定の候補順位付けと文字列化を含む試験です。製品Hostのグラフ実行・許可、実際の候補選択操作や文書への確定、途中の保護切替、実用辞書・TSFは未検証です。

同じコマンドに `--release` を付けた最適化ビルドでも両方300件全件正答しました。固定公式Wasm自体は同じです。

| 辞書行数 | 入力系列 | P50（ms） | P95（ms） | P99（ms） |
| --- | --- | ---: | ---: | ---: |
| 3 | 待ちなし | 1.186 | 2.372 | 2.803 |
| 3 | 20 ms | 1.427 | 2.587 | 2.628 |
| 3 | 100 ms | 1.436 | 1.739 | 1.766 |
| 1,000 | 待ちなし | 9.078 | 10.841 | 13.018 |
| 1,000 | 20 ms | 9.622 | 14.678 | 16.024 |
| 1,000 | 100 ms | 9.449 | 12.586 | 14.863 |

最適化時のJob CPUは3行281 ms、1,000行2,344 ms。1,000行では、最適化しても全系列のP95が10 msを超えました。試験Hostの辞書資源のJSON生成と、ゲスト内の読み込み・変換の両方が測定区間に入ります。この差は次の切り分けの対象です。

Store破棄とプロセス実終了は別です。この試験では各呼出しの後も同じプロセスが存続し、製品の現在の呼出しごとの終了保証は満たしません。通常Host経路の切替はこの試験に含めません。
