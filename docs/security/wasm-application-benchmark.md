# 実配布Wasmグラフの待ち時間を計測する

`benchmark-windows-application.mjs` は、Windows配布アプリを専用の一時データで起動する開発者向け計測ツールです。実公式Wasmのローマ字→同梱辞書→候補選択→文字列化を使用し、実行・入力経路・辞書の9対象をその接続だけ許可します。製品の隔離、燃料/メモリー制限、Workerの寿命、許可仕様は変更しません。Git/Cargoを利用者へ要求するものではありません。

## 再実行

Mainのソースと、検証対象の展開済みWindows配布フォルダーを用意します。ソースのルートから、その配布版に同梱したNode24.22.1を使えます。

```powershell
& 'C:\DIYIME2\runtime\node.exe' scripts/benchmark-windows-application.mjs 'C:\DIYIME2' --samples 100 --warmups 8 --poll-ms 5 | Set-Content latency.json -Encoding utf8
if ($LASTEXITCODE -ne 0) { throw '計測は成功していません' }
```

既存利用者のデータは使わず、毎回専用フォルダーを作成し、成功・失敗時に所有したアプリを終了してから片付けます。ブラウザーを開かず、子アプリのPATHを空にします。実ネットワークAPIや秘密値は使いません。レポートは全検査と終了が成功した後だけ標準出力へ出します。失敗時は終了コードが非0となり、成功レポートは出ません。フォルダー自体の信頼性や署名はこの検査で付与しないため、自分でビルド/検証した配布物を指定してください。

引数は `--samples` が1〜10000（既定100）、`--warmups` が0〜1000（既定8）、`--poll-ms` が1〜1000（既定5）です。6件・warmup0はCIの動作確認用で、性能の統計的根拠として扱いません。

## 測定区間と成功条件

- `initialReadyMs`: 新しいデータでの起動開始から公式48件の準備完了まで。初回導入を含み、OS全体のcold cacheを保証しません。
- `prepareMs` / `approveMs` / `activateMs`: 正確なグラフ確認・今回だけの許可・計画切替。`setupMs` は定義取得等も含みます。
- `firstRun`: 最初の変換。通常サンプルとwarmupの集計から除外します。
- `warmups`: 準備後の予備実行。結果と時間を残し、分位点には入れません。
- `samples`: 入力revisionの失効要求を送る直前から、結果がterminalで実処理4種類の数が全て0と確認できるまで。HTTP/JSON、入力失効・開始・照会・隔離実行・実終了を含みます。
- `existingCatalogReadyMs`: 同じ専用データで終了後に再起動した準備時間。計画と許可は復元せず、再起動も終了確認します。

固定順で辞書一致、未知読み、Unicodeを含む原文、空Data、入力途中の末尾、末尾確定の6種類を繰り返します。毎回の現在性、正常完了、復旧ではない結果、要求した出力、空Dataを含む正確なPacketを検査します。NoOutput・エラー・古い結果・停止未確認・欠けた物理状態を速い成功へ混ぜません。全52定義と同梱グラフ/辞書の一致、全配布ファイルのハッシュも検査します。

`summary` / `byCase` は nearest rank（昇順の `ceil(n*p)-1` 番目）によるP50/P95/P99/min/maxです。生の時間と固定のcase IDを残し、外れ値の除去や丸めはしません。100サンプルでも各caseは16〜17件に過ぎず、分位点の信頼区間や将来の最悪時間は保証しません。照会間隔による観測の遅れと照会負荷を含むので、異なる間隔の結果を同条件として比べないでください。

レポートの由来はbundle-manifest、Worker、Wasm、runtime DLL、グラフ、辞書のハッシュと配布元commit/種別、Node/Wasmtime/OS版です。開発作業フォルダーで生成された配布物のsourceCommitはnullのままです。入力本文・結果本文・秘密・RunKey・許可ID・個人フォルダーをレポートへ出しません。

## 保証範囲

これは小さな同梱テスト辞書グラフの待ち時間で、[Reference IME Latency](../performance-goals.md)ではありません。実用規模の辞書・TSF・キーからOS編集までの計測、実用速度達成の主張は対象外です。実行ごとの新しい隔離Workerは維持し、コンパイル済みコードや入力状態を使い回す最適化を導入しません。

CIは通常の配布物/launcher検査後、集計と失敗判定のテスト、実配布版での6入力を実行し、レポートを配布物artifactと一緒に保存します。機種共通の速度合格しきい値は設けず、正しい処理・実終了・レポート成立だけをゲートにします。手元の100サンプルの観測値はIssue/PRに由来とともに記録します。

## 基本記録のペア比較

`node scripts/compare-paired-windows-trace.mjs BUILT_FOLDER NEW_OUTPUT_DIRECTORY` は、同じ固定入力を記録OFFと基本記録で続けて実行します。各ケースの出現ごとに先行モードを交替させ、各群100ペアを3群、計600サンプル測ります。計測区間は入力更新から物理実行数ゼロの確認までです。記録開始、停止、終了後の回収とファイル保存は計測区間外で、実行中の150 ms間隔の照会は計測に含みます。

完了したペアは新規ディレクトリに順次保存されます。`complete-report.json` はアプリの終了と、既存カタログからの再起動・終了を確認した後に作成されます。`node scripts/verify-paired-windows-trace.mjs COMPLETE_DIRECTORY NEW_REPORT` で、保存済みペア、使用したスクリプトのハッシュ、実行順序、分位点を照合できます。CIでは2ペアで動作を確認します。

移行前の小辞書構成で測った3群のP95増分は −5.62%、+6.03%、+8.20%でした。300ペアとの照合が通り、記録欠落は0件でした。5%目標は2群で超過しています。公開版でも同じ測定条件を再現できるように手順を残し、この観測値は移行前の結果として扱います。

## 合成辞書の規模比較

同じ配布物を使い、`--samples 6 --warmups 0 --trace 2` で既定辞書を計測してから、`--synthetic-rows 1000` を追加して計測します。行数はヘッダーを除きます。合成辞書は既定の3行に重複しない別読みを足したもので、既存ケースの候補とスコアを維持します。

合成データは専用の一時データ領域に作り、結果の `provenance.syntheticDictionary` に行数、バイト数、ハッシュを記録します。配布元の辞書ハッシュは `provenance.dictionarySha256` に残ります。準備・有効化・実行の待ち時間を分け、Workerの工程は独立時計の区間として比較します。少数サンプルの診断なので、実用辞書の品質、候補数の影響、IMEの性能合否は別に評価します。

公開CIでは1,000行の出力と終了を確認します。`--synthetic-rows 10000` では有効化のHTTP 422を再現し、成功レポートは生成されませんでした。失敗した実行には待ち時間の集計がなく、手動での再現に同じオプションを使えます。[公開CIの診断ログ](https://github.com/pitapa79/DIY_IME/actions/runs/42019082667/job/127216983789)

[Issue #14](https://github.com/pitapa79/DIY_IME/issues/14) では、公開配布物の `official.wasm` と Wasmtime 50.0.1 DLLを、既存の `wasm_c_api_probe` で再生しました。辞書ノードの `prepare` に同じ合成TSVをバイト配列として渡し、配布アプリと同じ5,000万fuel・128 MiBで比較しました。3行と1,000行は `prepared: true` を返し、3,000・5,000・7,500・10,000行はすべてWasmtimeが燃料枯渇を返しました。10,000行の290,005 bytesは辞書ファイルの1 MiB上限内です。

配布アプリで観測した10,000行の `activate` は HTTP 422 / `worker-failed` でした。probeは同じゲスト処理の燃料枯渇を再現するための直接呼び出しです。配布アプリの隔離と終了の検査は、同じ配布物で行ったアプリ経由の測定で確認します。試した行数の間に成功・失敗の境界があり、行数だけで任意の辞書の成否を判断できません。[使用した公開配布物](https://github.com/pitapa79/DIY_IME/actions/runs/42010526169)

## 逐次入力と旧結果の失効

`node scripts/benchmark-windows-application.mjs BUILT_FOLDER --host-input-rounds 1` は、同梱小辞書で、逐次入力・Backspace・辞書一致を含む固定の7操作を3系列で実行します。前の操作の実終了を待つ系列、100 ms間隔、20 ms間隔です。後者の投入時刻は前の応答とは独立に予定します。Hostリクエストは直列のため、先行リクエストによる投入遅れも集計します。

入力失効を送る直前から、HTTP照会で正しい現在の出力を観測するまでと、実行の物理カウントがゼロになるまでを個別に集計します。高速な失敗、期限切れ、取消、旧入力に置き換わった操作は正答の分位点から外し、全試行数と内訳に残します。旧入力を照会しても結果本文が返らないことを検査します。診断はOFFです。候補選択・確定の文書状態、画面描画、OS入力の時刻はこのHost計測の範囲外です。CIの1ラウンドは正答・失効・回収を確認するスモークです。
