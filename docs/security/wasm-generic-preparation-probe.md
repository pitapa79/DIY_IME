# 汎用 Wasm の事前コンパイル予備実験

対象は #86 / #84。開始 main は `bb5293ba2bbbcd2d34a764221aeb2afaa4128470`。Windows x64、Wasmtime 50.0.1。#85 の検査用 `fixture.wasm.chain`（SHA-256 `1301ed6b7c9693bffe328cf8ae56a99c1db68a13f30abfe2604997a346dee2ca`）を使用。入力も出力も固定のテストデータ。

同一 Wasm、要求、DLL、燃料・メモリ上限で、24組を交互順に比較した。どちらの方式も一度限りの AppContainer/Job で実行し、元プロセスの正常終了と回収を確認した。再利用側はテスト所有のコンパイル専用 AppContainer が正常終了して返したアーティファクトを使用し、SHA-256 を Worker で照合する。先頭1バイトを改変した対照は拒否された。48件すべてで応答が完全一致した。

| 指標 | 各呼出しでJIT | 検査用コンパイル成果を再利用 |
| --- | ---: | ---: |
| 起動準備から終了・回収まで P50 / P95 | 85.52 / 88.74 ms | 65.22 / 66.55 ms |
| 子内のコンパイル/ロードと実行 P50 | 27.54 ms | 1.13 ms |
| Job CPU時間 P50 | 265.63 ms | 31.25 ms |
| Job ピークメモリ P50 | 43.94 MiB | 22.69 MiB |

初回のコンパイル専用プロセスの準備・実終了・回収は約930 ms（子内計測47.47 ms）。成果物は660,896バイト。この実験は通常 Host を通らず、作成・キャッシュ費用は反復呼出しの表に含まない。

## 同じ検査用 Wasm での Worker 寿命の比較

同じコンパイル成果を使い、使い捨て Worker の起動後ロード、入力前の事前ロード、保持 IPC を比較した。使い捨ては共通の入力で24組を交互順に測り、全応答と全実終了を確認。保持 IPC は同じ Node・設定・権限で、共通入力に加えて日本語と空文字を交互に送り、各入力で新しい Store/Instance を作成した。

| 方式 | 準備・終了を含む使い捨て1回の P50 / P95 | 入力を送ってからの別計測 |
| --- | ---: | --- |
| 毎回 JIT | 86.25 / 88.89 ms | |
| 成果再利用、入力後ロード | 65.11 / 68.33 ms | |
| 成果再利用、入力前ロード | 64.27 / 66.22 ms | 準備32.92 ms、正答0.24 ms、実終了1.93 ms（各P50） |
| 成果再利用、保持 | セッション準備49.72 ms、EOFから実終了2.58 ms・回収15.09 ms | 逐次200/200正答、P50/P95/P99 0.093/0.128/0.166 ms |

保持では20/100 ms間隔も各50/50正答。往復 P95 は0.329/0.294 ms。これはテスト専用 IPC の計測で、Core、通常 Host の公開条件、許可の失効を含まない。使い捨てと異なり、保持方式は個々の結果の時点でプロセスが終了していない。検証済みコード・入力先・権限がどこまで同一なら保持を許すか、異常終了の前後でどの結果を利用できるかは仕様上の判断が必要。効果の候補として #87 の複数モジュール・実グラフ・保護/取消の PoC に進み、採用判断は #88 で扱う。

## 次に比較する案

同じ通常 Host ワークロードで、起動前のコンパイル成果再利用と使い捨て Worker の準備を独立させて比較する。コンパイル再利用は同じ隔離枠で反復 CPU 費用を下げる可能性がある一方、単独では1呼出し約65 msの残存費用がある。未検証の第三者ネイティブ成果を受け入れる案は範囲外。汎用化に必要な証拠は、生成元の検証済み Wasm、DLL・エンジン設定、生成プロセスの正常終了、アーティファクトの改変・差替え拒否、入力・権限との分離、キャンセルと物理回収。今回のテストは製品での適用や仕様変更を承認するものではない。

再現には #85 の fixture を wasm32-unknown-unknown で release ビルドし、`DIY_GENERIC_PROBE_WASM` にその絶対パス、`DIY_COMPILED_PROBE_BUNDLE` に main CI Windows 配布版の展開先を指定する。

```powershell
cargo test --locked --lib compare_generic_artifact -- --ignored --nocapture
```

## 連続入力での使い捨て枠の補充

#20 では補充のたびに JIT が必要だった。#29 では固定公式 Wasm のコンパイル成果を共有しても DLL 検証・起動・実終了が残った。今回は同じ検査用 Wasm、DLL、コンパイル成果を両方式で使い、入力予定まで起動を待つ対照と、前のプロセスを実終了・回収してからすぐ補充する方式を比較した。1枠または2枠で、2枠では予定入力を交互に割り当てた。32件を各方式2試行、計512件すべて正答し、すべて元プロセスの正常終了を確認した。

| 入力間隔 | 枠 | 方式 | 入力予定までに準備済み | 予定から実終了確認 P50 / P95 / P99 | 予定から回収 P95 |
| --- | ---: | --- | ---: | ---: | ---: |
| 20 ms | 1 | 入力時起動 | 0/64 | 731.64 / 1376.28 / 1442.19 ms | 1388.92 ms |
| 20 ms | 1 | 事前準備 | 2/64 | 668.02 / 1310.58 / 1427.12 ms | 1322.28 ms |
| 20 ms | 2 | 入力時起動 | 0/64 | 257.32 / 447.86 / 476.43 ms | 464.14 ms |
| 20 ms | 2 | 事前準備 | 4/64 | 208.93 / 424.93 / 446.10 ms | 438.44 ms |
| 100 ms | 1 | 入力時起動 | 0/64 | 53.02 / 56.04 / 59.37 ms | 68.95 ms |
| 100 ms | 1 | 事前準備 | 64/64 | 2.55 / 3.32 / 3.46 ms | 15.81 ms |
| 100 ms | 2 | 入力時起動 | 0/64 | 53.12 / 57.93 / 94.39 ms | 70.63 ms |
| 100 ms | 2 | 事前準備 | 64/64 | 2.45 / 3.06 / 3.52 ms | 16.18 ms |

起動準備 P50 は各条件で約50–52 ms、単体 Job CPU P50 は31.25 ms、単体 Job ピークメモリ P50 は約22.7 MiB。集計にはコンパイルの初回費用を含めず、メモリは2枠の合計ピークを表さない。事前準備の最初の1枠あたり1件は入力列の開始180 ms前から準備できる条件。20 msではこの初期在庫を消費した後、2枠でも1枠あたり40 ms周期に補充が追いつかなかった。すべての入力を完了させるための待ちを計測しており、入力置換を行う通常 Host の結果件数や応答時間には換算できない。

1段・100 msでは入力前の準備で待ちを大きく減らせる。20 msの常用や複数段への効果はこの試験から認定できない。通常 Host での枯渇時の入力置換、許可変更や保護時の配送拒否、回収中の予約維持を確認してから採否を判断する。

```powershell
cargo test --locked --lib compare_generic_one_shot_refill -- --ignored --nocapture
```
