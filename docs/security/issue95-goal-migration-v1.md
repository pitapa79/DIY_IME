## 1. 移行対象と保全

#95の旧指標は、通常Windows Hostで任意の安全条件を満たす軽量Wasmの基盤追加遅延P95 < 10ms / P99 < 20msを、測定・安全・通常経路統合と合わせて達成条件にしていた。#106はこの一律の数値必達をS0から外し、S1には技術目標として残す方針である。**過去の測定や失敗を削除し、旧Goalを達成したように書き換える移行ではない。**

移行前に、#95の全文・更新日時・URL・UTF-8本文のSHA-256と、関連PRの完全HEAD SHA・採用状態を保存し、移行記録に結び付ける。既存の再開案内・元の受入条件・作業記録は、履歴と分かる形で参照可能に保つ。現状の進捗prefixと、元の要件本文も区別する。

この仕様案の発効前は#95を閉じず、旧条件での未達を維持する。発効後も過去の結果を「旧10/20ms達成」と改称せず、新しいGoal A/Bの状態へ対応付ける。

## 3. 親Goalと子タスクの作り方

承認後の#95はA/Bを追跡する親Issueとし、未検証のチェックを自動的に完了させない。Goal A、Goal B、S2研究はそれぞれ専用Issueへ分け、下記の受入条件を対応付ける。各実装は1 Issue = 1 branch/worktree = 1 PR。未採番の子Issueを作成済みのように表記しない。

### Goal A: S0の保証維持・性能改善

- [ ] S0の適用範囲、単回使用・実終了/必要回収、許可・保護・現在性を文書化し、実Windowsで安全回帰を確認する。
- [ ] 仕様の構成/入力/変更/寿命の測定表に、証拠の場所、通常経路・候補の区別、件数、分布、CPU/RAM、終了・回収、未対応理由を記録する。
- [ ] 支配的な固定費を特定し、各改善の仮説、採用/棄却/要修正、同一条件の根拠を残す。
- [ ] 採用する改善を通常Hostで検証し、S0保証・正答・既存契約を維持する。必要な実装検査・最新CIと適切なマージ条件を満たす。
- [ ] 未採用候補とmainで有効な改善を分け、残る遅延、未検証範囲、再現と引継ぎを記録する。
- [ ] 以上を独立に判定する。**10/20ms未達だけでAを未完了にしない**。完了後の改善は後続Issueへ分ける。

### Goal B: S1の技術的実用化

- [ ] Hostが実コード・能力・設定・依存・保持リスクを照合する資格と、失効・再審査・安全なS0移行/拒否を実装する。
- [ ] Node別AppContainer、入力ごとの新Store/Instance、有限な寿命/予約、元所有者の停止・最終回収を実装する。
- [ ] 維持保証と正常入力ごとの物理終了/プロセス内残存に関する緩和、保護・入力先境界を説明する。
- [ ] 単段・代表的複数段と仕様の測定表を評価し、基盤追加遅延P95 < 10ms / P99 < 20msの達成/未達・条件・分母・欠測を記録する。
- [ ] 初回/warm/逐次/100ms/20msと取消・障害後の最新入力復旧を、正答、失効、拒否/busy、時刻の始終点と共に測る。
- [ ] Session/文書/入力先、計画・設定・辞書・権限変更、保護、取消、異常終了、再生成、長時間運用、完全な最終回収を安全回帰で確認する。
- [ ] S0と既存固定公式経路に回帰がなく、必須Windows CIが成功し、適用制限・残る性能問題・未検証条件を記録する。
- [ ] 技術的に実用化を判定できる証拠をまとめる。重大な未解決の安全・応答問題があれば**要修正**とし、単段の速さ・CI成功だけで完了にしない。
- [ ] S1の技術的判定と製品採用を別記し、製品採用・default変更には別途の仕様/マージ承認を得る。

A/Bに共通する基盤・回帰は共有証拠へリンクできるが、片方の完了で他方を完了にしない。Bの審査基盤・回復改善を進めるために、Aの完了やS2研究の完了を一律の前提にしない。実装ごとの実際の依存PRだけを明示する。

親#95は、仕様移行とA/Bそれぞれの受入証拠・完了判定が揃った時点で判定する。S2やTSF・配布の完成を新たな必須条件にしない。Bの技術的完了を製品採用済みと誤記しない。

## 5. S1製品採用に向けた未承認の数値提案

**以下はメンテナー判断用の推奨案であり、仕様の承認済み合格値ではない。** 本仕様PRのマージ承認に、下表の数値の採用を暗黙に含めない。数値を採用する場合は、対象条件と承認を別途明記する。

対象は準備完了後、逐次/100ms/20msの入力・取消による置換から、最後に受領した入力の現在の正答が公開されるまで。初回準備完了待ちや計画/辞書切替は別表で計測し、まだ許容値を固定しない。重い固有計算を持つ任意Nodeにこの値を一律強制しない。

| 軽量構成 | 最新入力応答P95の候補 | P99の候補 | 最大値の候補 |
| --- | ---: | ---: | ---: |
| 単段 | 50ms | 100ms | 200ms |
| 4段 | 75ms | 150ms | 300ms |
| 20段 | 100ms | 200ms | 500ms |

推奨理由は、既存の通常応答の50ms超抑制の目標を単段の出発点とし、多段にも有限の復旧予算を置くためである。段数比例で数百ms〜秒の遅延を無条件に許容する案は推奨しない。#105の暖機後22〜25msという観測と、取消後418/810msという差を検出できる水準として提案する。ユーザビリティ実験で実証した閾値ではなく、Reference IMEの通常応答10/20ms目標やCore目標の代替でもない。

採用前の測定計画として、次も併せて提案する。

- 各構成・入力間隔・実行条件について少なくとも1,000件の**最終入力**を得て、3回以上の独立した測定を実施。1,000件は測定計画の提案であり、統計的な一般保証の宣言ではない。少数バーストのP99だけでは判定しない。
- 合意した複数のWindows環境でCPU/メモリ/OSと枠・寿命を固定し、環境別・バイナリ別に判定。具体的な最低対応環境は別途決定し、CIの速い一台だけで保証しない。
- 入力予定→発行/受領、Host受付→正答公開、最終物理回収をそれぞれ記録。再試行・busy・欠測・未完了を除いて速いpercentileだけを作らない。
- 古い結果の公開・誤答・最新入力消失は0件を要求。取消/保護/失効/文書切替/異常・再生成と長時間運用の安全回帰、S0/既存固定公式経路の回帰、最終回収、有限なCPU/RAM/Worker枠を前提にする。

判断事項は、表の値、初回準備・変更操作の許容応答、最低環境、運用時間・負荷条件、資源予算と採用範囲である。未決定の数値を埋めてGoal Bや製品採用を合格扱いしない。技術改善や追加測定の実施は、この数値承認待ちと切り離して進められる。
