# Wasm Node package / Host catalog v1

Issue #272; follows [v3 adapter](wasm-v3-adapter.md). Windows x64 implementation.

A .diynode file contains one Node and one binary wasm32 module. There is no archive extraction. Its 24-byte header is ASCII DIY2NODE, little-endian u32 format version 1, u32 UTF-8 manifest length and u64 module length. The exact manifest and Wasm bytes follow. Overflow, truncation, trailing data, unknown manifest fields, unsupported runtime/API, system Node replacement, invalid definitions and mismatched SHA256 are refused.

Manifest camelCase fields: packageId, version (SemVer), displayName, runtime ("wasm32"), guestApiVersion (1), node (existing NodeDefinition), moduleSha256 (64 lowercase hex), capabilities ([{id,binding}]). IDs/bindings are logical aliases, never paths, URLs, credentials or grants. The manifest must describe exactly one guest definition. A producer must preserve the JSON numeric representation of the actual definition, including floating defaults.

PackageLimits are Host-selected size policies, not global limits on user graph design. Defaults: manifest 1 MiB, Wasm 64 MiB, total 65 MiB + 24, catalog 16 MiB, import batch 512 MiB. PackageVerifier captures bytes and runs describe plus default-config validation in the actual AppContainer/Job Worker; it compares the resulting definition with the manifest. Arbitrary code is never loaded into Core. Supported dictionary.read, network.request and secret.use declarations use typed Host brokers; see wasm-dictionary-broker.md and wasm-network-broker.md. Unknown capabilities are refused. Installation grants no authority, and runtime requires configured providers and current explicit consent.

The authorization SHA256 includes package ID, exact module digest, complete Node definition and sorted capability declarations. Display label and package version alone cannot create authority. WasmNode's opaque grant target also includes this authorization subject, the captured Worker/DLL/module identity, session, plan and Node instance. Installation itself never approves execution. Metadata-only changes preserve the authorization subject; changed code, ports/default/config schema or capabilities change it.

Catalog::open uses an existing Host-selected data directory. Metadata never supplies a storage path. review verifies every candidate before writing package objects or the index, rejects duplicate package IDs and kind collisions across the resulting catalog, and returns an opaque in-memory ImportPlan plus a serializable review. All successful candidates become visible together. This API must run on a Host preparation thread, never the Core actor/UI thread.

ChangeKind distinguishes new, unchanged, metadata, upgrade, downgrade and sameVersionRebuild. SemVer precedence ignores build labels. Lower versions and same-version changed implementations require explicit confirmation. requiresPermissionReview identifies changed authorization subjects; it is information for the later permission UI, not an execution grant.

commit consumes the plan, holds an exclusive Windows file handle on catalog.lock, rechecks the exact prior index digest/revision, writes content-addressed objects/<packageSHA256>.diynode via synced temporary files, then replaces catalog.json with a same-directory MoveFileExW operation. The revision is a canonical decimal u64 string for JavaScript. A stale review cannot overwrite a newer catalog. Readers see the old or new complete index. This is atomic visibility, not a power-loss durability guarantee. A failed commit may leave unreferenced code objects; it does not expose a partial batch. Installed reads revalidate framing, digest and manifest. Corrupt existing objects are refused, not silently replaced.

Storage root/direct children must be regular directories/files without reparse points; reads use OPEN_REPARSE_POINT and check the opened handle. The Host owns this directory and never gives its ACL to a guest. This does not defend against another process already holding the user's full filesystem authority replacing ancestor paths. The catalog is an installed inventory, not trusted executable state: loaded packages still need live isolated verification and current explicit execution permission. Existing running plans retain immutable code captures; GUI update/removal must revoke affected gates and clear delivered UI buffers before activating replacements.

Developer tool diy-ime2-node-package:

- pack MANIFEST WASM OUTPUT writes a new file and refuses overwrite.
- inspect PACKAGE validates framing/metadata/digest only; isolatedVerified is false.
- import DATA_ROOT WORKSPACE WORKER DLL PACKAGE... verifies all packages and prints a review. --commit applies the reviewed batch. --allow-downgrade and --allow-same-version-rebuild explicitly acknowledge those changes. It creates the Host-selected directories and uses the bounded probe policy; the library permits a selected WorkerPolicy. No Git/Cargo is needed to run a distributed executable. Import issues no execution grants.

scripts/check-wasm-v3.ps1 runs the actual AppContainer package/catalog integration alongside the v3 adapter regression. It covers preflight/no disk mutation, successful multi-import, stale plans, duplicate IDs/kinds, exclusive locking, mismatched definition, unsupported capabilities, metadata, upgrades, explicit downgrade/rebuild, code identity and corrupt objects. Unit tests cover framing corruption/truncation/trailing bytes, identity changes, strict metadata and system Node refusal.

GUI management, current/saved permissions, flow approvals and typed dictionary/network/secret brokers are implemented in the linked security documents. Official compiled-data/bootstrap is described in [official-node-distribution.md](official-node-distribution.md). Complete application distribution, default cutover and removal of old in-main processing copies remain subsequent work.
Installation and runtime proofs are now [separate opaque types](wasm-installation-proof.md). Catalog imports can install supported dictionary declarations before resource configuration; installed code still requires full runtime verification and current explicit consent.
