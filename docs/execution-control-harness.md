# 期限・協調取消・遅延結果の独立試作

状態: [Issue #48](https://github.com/pitapa79/DIY_IME2/issues/48) の独立実験。正式 Node API や本番 Engine の実装仕様ではない。
開始基準は `2d7a26187b686c74132731d5b00c3b6dc7bb43d7`。
[Issue #44](https://github.com/pitapa79/DIY_IME2/issues/44) の提案書は開始時点で未保存のため、以下の順序と上限は試作上の仮定として評価する。

## 実行

```powershell
cargo run --locked --example execution_control_harness
cargo test --locked --example execution_control_harness
```

モデルとテストは [examples/execution_control_harness.rs](../examples/execution_control_harness.rs) に閉じる。
標準ライブラリだけを使い、sleep、実時計、ネットワーク、スレッド、外部 LLM/API、辞書、OS 登録を使わない。

## 仮定

- ホストがイベントの仮想時刻を指定して単調時計を進める。時刻の単位は任意。後退は拒否する。
- 完了はホストが明示する。時計を進めただけで仕事は完了しない。
- run 受付時を期限の起点とし、キュー待ちも予算に含める。
- 期限と完了が同時なら期限を先に扱う。同時刻の明示イベント間はスクリプト記載順とする。
- 結果選択と資源回収を分け、取消要求だけでは枠を解放しない。
- 全世代トークンと仕事 ID はホストが真正に配送し、再利用しない。本番には別途その保証が要る。

## 時計と到着順

`event(at, action)` の `advance` が時計を進める唯一の入口。次のイベントへ飛ぶ場合も、途中の期限・キュー失効・取消猶予の各時刻を順番に処理する。同時刻の内部タイマーはキュー失効 → run 期限 → 取消猶予の順。その後に明示イベントを処理する。したがって期限ちょうどの完了は、呼出順にかかわらず新しい候補として採用されない。すでに届いていた候補は期限時に選べる。

同時刻の二つの完了はスクリプト順になる。実時計で観測できない真の同時性を証明する規則ではない。本番で採用するなら、到着の線形化点とタイマーの優先順位を別途合意する必要がある。

`Observe` は待機中であることを記録するだけで、期限を延長しない。予算は必ず有限とする。より長く待ちたい構成は run 開始時に大きい予算を与える。本試作には実行途中の期限延長や無期限待機はない。

## 結果選択と停止の状態

`SelectionPolicy` を scheduler と分離した。方針が受け取るものは完了/期限という契機と利用可能な候補であり、実行枠の管理を行わない。

| 試作側の方針 | 速い経路が先に完了 | 遅い経路が期限前に完了 | 期限 |
| --- | --- | --- | --- |
| `FirstAvailable` | その時点で採用 | 最初の完了なら採用 | 到着済み候補、なければ候補なしで終了 |
| `PreferSlowUntilDeadline` | 候補を保持して待機継続 | 遅い候補を採用 | 到着済み候補へフォールバック、なければ候補なしで終了 |

後者は同じ経路の再完了があれば最新の一件だけ保持する。経路の速い/遅いは識別ラベルであり、実測速度や品質判定ではない。文字列は実行例が所有する静的なテスト値。Packet、Data/NoOutput/Error、意味的な候補スコア、実際の失敗回復はモデル化しない。`DeadlineWithoutResult` は制御上の終了理由であって製品の NoOutput ではない。

結果決定後は未開始キューを破棄し、未選択の実行中経路へ取消要求を記録する。決定は同じ世代で変更しない。全仕事の終了を待ってから返す必要はないが、結果を返した時点で仕事や副作用が消えたことにはならない。

```text
Running ──完了──> 資源回収 + 候補として配送可能
   │
   └─取消要求──> CancelRequested ──取消確認/完了──> 資源回収のみ
                       │
                       └─取消猶予──> Stalled ──取消確認/完了──> 資源回収のみ
```

`CancelAck` は「取消を受け取った」ではなく「処理が終了して資源を返せる」というホストの明示的な確認を意味する。実行中状態への unsolicited ack は拒否する。取消要求後に通常完了した場合も枠は回収するが、候補は破棄する。副作用の巻き戻しと同期 Rust 関数の強制停止は保証しない。

## 世代と資源回収

完了と取消確認は `(JobId, session, plan, run, input)` を照合する。違うトークンは結果の採用にも枠の回収にも使えない。重複完了と未知 ID も無視する。

`Replace` は入力更新、計画切替、新しい run、セッション変更の模擬操作。候補と決定を消し、新しい期限を受付時刻から設定し、旧キューを破棄して旧実行へ取消要求する。旧仕事を active 表から即削除しない。旧世代の真正な完了/取消確認は、その仕事の資源回収にだけ使え、新世代の結果としては配送しない。取消確認前に新しい run を開始しても、旧仕事が枠を占める。

この単一モデル内では session を単調増加させ、同じ session 内の plan/run/input は減らさず、同一 tuple への置換も禁止する。仕事 ID は置換でもリセットしない。オーバーフローは拒否し、取消猶予の加算だけは最終 Tick へ飽和する。現実のセッション ID はランダムな文字列でもよく、本試作の数値順序を製品へ要求するものではない。本番では再接続・ロールバックを含むトークンの一意性、入力内容との対応、偽装されない配送を別途保証する。

## 滞留を有界にする案

| 資源 | 試作の上限・処理 |
| --- | --- |
| 実行中・取消待ち・滞留中の仕事 | 合計 `slots` 件。同じ枠を全世代で共有 |
| 未開始の要求 | `queue` 件まで FIFO。満杯時は即拒否し、自動再試行しない |
| キュー待ち | 受付から `queue_wait` Tick。期限ちょうどの枠回収より失効を優先 |
| run の待機 | run 受付から有限の予算。終了時にキューを破棄 |
| 取消確認待ち | 要求から `cancel_grace` Tick 後に `Stalled` を通知。枠は保持 |
| 候補と観測履歴 | 各経路一件、trace は `trace` 件のリング。古い診断は脱落 |

サンプル設定は実行2、キュー2、キュー待ち8、取消猶予3、履歴128。固定の製品上限ではなく、ホストが提供する資源制御を試作側で設定する値である。

完了しない仕事のためサービスが進まなくなることはある。しかし猶予後に枠だけ解放して次々起動することはせず、キュー待ちは失効し、受付は有界に拒否できる。`Stalled` は安全な強制回収を意味しない。進行性が必要なら、ホストが外部プロセス等を隔離し、停止・資源回収を確認した後に枠を返す契約が別途必要。この試作には kill 操作はない。

## 現在の Core との差分と責務

現在の [runtime.rs](../crates/runtime/src/runtime.rs) の `Engine::run_internal` は同期処理で、各ノードの全入力解決後に `execute` を呼び、上流エラーなら Blocked、必須入力の NoOutput なら Skipped とする。[コア契約](core-architecture-v0.1.md) と [常駐プロトコル](session-protocol.md) は維持する。現在のブリッジは要求を直列送信し、送信後タイムアウトではセッションを無効化する。本試作はその要求や10秒の監視タイマーを変更しない。

経過時間ノードを通常の同期グラフに追加するだけでは、重い `execute` 中に時計を観測する実行機会がない。合流ノードも全入力解決を待つため、速い候補が届いた時点で遅い入力を待ち続けるか決める入口がない。期限通知、完了の配送、取消要求を扱う実行境界が必要になる。

| 層 | 本番で検討する責務 | 試作での対応 |
| --- | --- | --- |
| Core / 実行境界 | 完了・時計・期限・取消・世代照合・配送、実行資源の制御 | `Harness` のイベント遷移と上限 |
| 構成 / ノード | 候補の意味、待機・採用・フォールバック方針、協調取消への対応 | `SelectionPolicy` と模擬完了イベント |
| ホスト | 単調時計の駆動、イベントの正当な順序とトークン、入出力更新、接続監視、必要時の隔離 | 固定スクリプトが代行 |

Core は外部変換の意味や遅い候補の品質を決めない。協調取消に従わない処理の強制停止と副作用の補償は、この scheduler の能力ではない。

## 自動検査と読み取り例

テストは固定イベント列の trace 全体の再現、二つの方針の結果差、待機継続、期限前/同時/後の完了、候補なし期限、明示取消、取消確認、取消後の遅延/重複結果、4世代の個別不一致と置換を検査する。加えて FIFO・キュー満杯・失効・永続滞留・旧世代回収後の新要求開始、時計後退・世代再利用・加算オーバーフロー拒否、候補/履歴の上限も確認する。

実行例の主要部分は次の順序になる。

```text
0: fast / slow を開始
2: fast 完了、候補を保持（まだ選ばない）
4: Waiting
10: Deadline → fast 採用 → slow 取消要求
10: slow 完了 → 資源回収 → 結果破棄
```

検査コマンド:

```powershell
cargo test --locked --example execution_control_harness
cargo run --locked --example execution_control_harness
cargo test --locked
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
```

## 本番へ移せない仮定と設計へのフィードバック

この検査は仮想時刻の機能試験であり、実スレッドの安全性、性能、実際の強制取消を証明しない。単一スレッドの真正な完了イベント、静的な小さい文字列、非ブロッキングで正しい選択方針、信頼された取消確認、ホストの一意な世代発行を仮定する。実装の reentrancy、panic、プロセス故障、輸送遅延・順序逆転、実メモリ量、UI 配送、外部 API の副作用や課金は検査しない。

#44 / [後続評価 #49](https://github.com/pitapa79/DIY_IME2/issues/49) へ返す判断材料:

1. 期限同時完了の規則を決めないと、同じ候補でも採否が変わる。本試作の期限優先は採用候補の一案。
2. 結果を古いものとして拒否しても、資源回収用の完了通知まで拒否すると枠を回収できない。結果配送と仕事の所有権の照合を分ける必要がある。
3. 取消猶予後の自動的な枠解放は、実処理が継続する場合に上限を破る。停止を確認できない仕事は枠を保持し、入場制御で有界にする案を比較すべき。
4. run の処理期限と接続/プロセスの生存監視は別物。試作で長く待てたことを、現行ブリッジに接続できる証拠にしない。

本番接続の前に、#44 の契約の該当部分をユーザーが採用し、仕事の受付/完了/取消確認/状態取得、世代の発行元、ホストの時計と回収保証、既存同期 API との互換性、輸送・負荷試験を別タスクで確定する。この2ファイルのマージは仕様採用を意味しない。戻す場合はこの example と文書を削除すればよい。
